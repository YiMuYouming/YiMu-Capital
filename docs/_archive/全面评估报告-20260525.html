数据管线 — 可靠性与盲区
架构核心
做得好的
  • CACHE 热启动（cache_dump.json）保证 bridge 重启后不白屏
  • atomic_write_json + FileLock 防止多进程写入损坏
  • 竞价快照选在 9:28（给 iwencai 留足处理时间）
  • 三层 PnL 保护机制（gen 不覆盖实时持仓）
  • 成交额对比用 update() 而非赋值——避免了昨天数据被抹的问题
P0 iwencai 数据质量隐患
10 分钟轮询一次，但 pywencai fallback 是同步阻塞的，每次 poll 要跑 8 个查询。若 OpenAPI 超限或 pywencai 报错，整个 iwencai 数据域会静默退化为旧值，前端没有任何「数据过期」警告。建议在 CACHE["iwencai"] 增加一个 _fetch_time 字段，前端组件据此显示「数据已过时 N 分钟」警告。
P1 竞价快照只跑一次
snapshot_auction.py 只在 9:28 执行一次，如果当天 bridge 重启，竞价快照永远是 9:28 的数据，W06 会持续显示过时的 5 维信号灯。建议增加一个 10:00 备份快照。
P1 yesterday_compare 数据脆弱
昨日成交额对比依赖 PyTDX 的 15 分钟 K 线数据，连接在行情波动时容易抖动。当前 collect_yesterday_compare 没有独立日志，如果这个数据丢了，W04 成交额对比就永久空白。建议增加采集成功率的监控指标。
P2 sentiment_auto.json 是 append 操作
每次快照追加到文件末尾，若当机时文件写入一半，可能损坏 JSON 结构导致 W05 读取崩溃。建议换成 append-only 格式（每行一个 JSON），或者写临时文件再 rename。

需修复的组件
P0 W05、W06 数据源不规范
这两个组件不通过 DataStore 订阅，而是直接 fetch() 文件。破坏了 SSOT 架构——数据不会随 bridge CACHE 更新而刷新，GridStack 重排时组件行为不一致。应该将这两个文件也纳入 DataStore 的订阅体系。
P0 W12、W13 代码重复
两个组件近 100 行几乎完全相同，只是数据源不同（连板池 vs 趋势池）。维护成本翻倍——改一个逻辑要改两处。应该抽象出 StockPoolWidget 基类或共享渲染函数。
P1 W11、W12、W13、W16 事件监听器泄漏
addEventListener 没有通过 _domListeners 追踪，组件销毁时监听器残留在 DOM 上。每次数据刷新都添加新监听器，造成内存泄漏。建议统一改用事件委托模式，在基类层统一处理。
P1 W14 缺少 updateTimestamp()
风控面板 W14 在 render() 末尾没有调用 this.updateTimestamp()，导致数据新鲜度指示器始终显示灰色（dead）状态。
P2 W08、W09 profitFx.indexOf('好') 逻辑 bug
"不好" 会被错误匹配为正收益。字符串判断太粗糙，建议用精确的 === 或枚举对照。
P2 W10、W21 每次 render 都发 fetch
W10（板块）和 W21（梯队）每次 _renderBody() 都调用 _loadInsights()，没有 _loading 状态锁，导致频繁重复请求。
P2 W12/W13 买入颜色语义不一致
W12 的「追」用红色，W13 的「买入」用绿色。两者都是买入信号但颜色相反，容易混淆。建议统一：买入 = up（红），红色代表「可执行/积极」。

AI / LLM 系统
潜力最大
做得好的
  • 14 分钟自动研判，后台运行，浏览器关了也跑
  • ReAct 信号验证层，防止幻觉信号
  • 3 轮对话记忆，W20 监控卡片 + 浮动聊天框双入口
  • DeepSeek V4-Flash 成本可控（Flash 模型）
P1 LLM 输出格式依赖标记词
后端用 [TEXT]/[SIGNALS] 字符串分割来解析输出，如果模型格式稍变就静默失败。当前没有对解析结果的 schema 校验——signals 数组可能为空或格式错误，前端显示无信号但不报错。建议增加 JSON-mode 输出或在 prompt 中要求能被 json.loads 解析的格式。
P1 ReAct 验证过于宽松
对每个信号只检查基础条件，但不验证信号与当前情绪区间的匹配度。例如在冰点（情绪 <20%）时，模型输出 BUY 信号仍会被标记为 verified。建议增加情绪-信号的联动校验：冰点不输出 BUY，双冰不追涨，高潮期不追连板。
P2 系统 Prompt 无版本控制
LLM_RULES.md 是纯文本，每次修改即时生效，没有版本记录。如果改错了规则，LLM 的行为会悄悄改变，但没有回滚机制。建议在 llm_insights.json 的每条记录中保存当时使用的 rules hash。
P2 手动/自动模式共享同一个流
如果自动研判出错（iwencai 数据异常），手动问答也会受影响。建议分离处理：自动研判在发送前增加数据完整性校验，手动问答更宽容。
P3 对话历史只存今天
历史对话没有长期保存，如果想回顾「上周五 AI 说了什么」只能翻笔记。建议增加周度归档，或在 pnl.db 的 llm_insights 表中保留所有历史。

UI/UX 设计 — 暖砚风格
体验层
做得好的
  • CSS 变量系统（54 个变量）覆盖完整，主题一致性高
  • tabular-nums lining-nums 数字等宽，阅读体验好
  • 红涨绿跌 + 符号双保险，符合 A 股习惯
  • Widget 分类色条（决策/数据/风控/工具）视觉清晰
  • GridStack 可拖拽布局，个性化体验好
P1 W20 浮动聊天框层级冲突风险
z-index: 3000 硬编码，如果将来有其他浮层需要更高层级会产生覆盖问题。建议改用 CSS 变量管理层级。
P1 没有暗色模式
长时间盯盘的投资者（尤其是晚盘）会希望暗色主题。当前后台主题色是暖砚白（#F7F5F3）。建议增加 prefers-color-scheme: dark 支持，或提供主题切换开关。
P2 响应式布局缺失
GridStack 配置固定 column: 12，笔记本（1366×768）上组件过于拥挤。W22 的 Canvas 图虽然处理了 DPR 缩放，但图表区域在窄屏下容易被压缩。
P2 组件刷新时无骨架屏/过渡
数据刷新时组件内容直接替换，没有淡入淡出或骨架占位。对于 W04（全景）和 W10（板块）这类数据量大的组件，刷新瞬间的视觉跳变明显。
P3 全局快捷键无冲突检测
R/P/Ctrl+S/A/Ctrl+F 等快捷键没有检查是否与浏览器或系统快捷键冲突。A 键在某些输入法下可能失效。

交易决策支持
核心闭环
▶
当前链路 LLM_RULES.md (规则) → W08/W09 (规则执行检查) → W15 (操作录入) → W17 (今日操作展示) → W22 (PnL闭环)
P1 缺少「信号 → 操作」的确认流程
W08/W09 显示「买入/等待/降级」信号，但信号到 W15 录入之间是手动操作。这个 3 秒的摩擦在紧张的盘前/盘中会显著影响决策执行率。建议在 W08/W09 增加「录入操作」快捷入口，直接调起 W15 的买入表单并预填标的名称。
P1 W03 仓位上限不响应熔断
W03（仓位计算）的上限从 data.style.总仓位上限 读取，这是每日基线。但如果熔断触发（由 W07 检测），W03 不会自动更新上限。需要增加一个 DataStore 订阅：当 risk.熔断触发 变化时，W03 重新渲染。
P2 W02 风格检测是每日一次静态值
风格分数在每日 8:30 由 style_detect.py 生成，但盘中风格可能改变（W02 无法感知）。建议增加盘中风格再评估机制，用 iwencai 的板块热度数据驱动动态调整。
P2 没有止损提醒的实际触发
LLM_RULES 里明确写了止损规则（连板 5%、趋势 7%），但当前系统只做「展示」，没有主动提醒。W14 可以显示持仓成本和现价，但没有计算哪个持仓已触及止损线并主动报警。
P3 冰点/双冰检测是静态的
W19 只在午盘复核时展示双冰状态，但双冰是前置条件，应该在开盘前就判断（gen 阶段）。建议将双冰检测自动化：用 sentiment_auto.json 的历史情绪数据自动计算。

个人投资者场景适配
信息降噪
⚠
核心痛点 作为个人股票投资者，核心痛点是个信息过载和决策疲劳。系统当前 22 个组件是信息密集型设计，但有些地方反而制造噪音。
需要精简的
P1 22 个组件过多了
实际盘中操作只需要盯 5-8 个核心组件：W04（全景）、W07（高潮守护）、W08/W09（W1/W2 窗口）、W15（持仓）、W22（PnL）。其余组件可以折叠或默认隐藏。建议增加「精简模式」开关，切换后只显示核心组件，减少认知负担。
P2 W21 梯队面板太复杂
571 行代码，日期 tabs、概念 tags、多选排序、LLM 洞察、板块过滤——信息量过大。实际盘中查看梯队只需要：今天有哪些连板梯队、各梯队高标是哪只。建议拆分为「盘中快速查看」（表格）和「盘后复盘」（完整面板）两个视图。
P2 数据新鲜度显示不统一
部分组件有 data-timestamp 指示器，部分没有（W14 就缺少 updateTimestamp()）。在长时间运行时，用户无法判断哪个数据已经过期。建议统一所有组件的数据新鲜度指示器。
需要增强的
P1 增加「盘前预案」功能
当前系统以盘中盯盘为主，缺少盘前决策文档化。可以在 W16（报数面板）增加一个「今日预案」文本区，记录开盘前的核心判断：今天的主要机会在哪、哪些标的不碰、如果高开/低开怎么处理。
P1 成交额感知的量化阈值
W04 显示成交额和「较昨日同期」，但没有告诉你这个变化是好是坏。A 股经验规则：成交额较前日放大 30% 以上是活跃信号，萎缩 20% 以上是冷清信号。建议增加「量能信号」指示（放大/正常/萎缩），直接显示在 W04 成交额旁边。
P2 持仓联动到 LLM 研判
如果持仓中有股票出现异常波动（跌幅 > 3%、涨停、炸板），应该主动触发专项研判，而不是等 15 分钟一次的自动轮询。建议增加持仓异常监测：一旦持仓标的价格变化触发阈值，立即在 W20 显示「持仓异动提醒」。
P2 增加交易日志的「原因-结果」对照
W15 的操作录入有「原因」字段，但 W17 展示时没有充分利用。建议盘后（15:05）自动拉取当日收盘数据，计算每个操作的实际效果（买在 X，收在 Y，盈亏 Z），作为 AI 复盘的学习素材。

架构与代码质量
工程化
做得好的
  • YiMuWidget 基类设计合理，生命周期清晰
  • DataStore 的三层合并架构是正确的抽象
  • SSOT 审计已识别并记录了关键数据域
  • CSS 变量系统避免了样式碎片化
P1 组件间通信机制缺失
当前组件完全独立（通过 DataStore），但有些场景需要跨组件协调：W08 买入信号 → 自动触发 W15 表单预填，W07 高潮告警 → 同步关闭 W03 的可开仓位显示。这种联动目前靠 window._llmChat 这样的全局 hack 实现。建议在 store.js 增加一个事件总线：DataStore.on('signal:buy', callback)。
P1 _domListeners 追踪不完整
基类设计了 _domListeners 数组来管理事件清理，但 W11/W12/W13/W16 都没有使用它。建议在基类的 mount() 里增加一个 lint 提示，如果组件添加了未追踪的监听器就报警。
P2 gen_dashboard_data.py 是单点依赖
整个系统的 Layer 1 基线依赖 gen_dashboard_data.py 的正确运行，但格式没有 schema 校验。如果复盘笔记格式稍有变化，gen 可能静默失败或输出错误数据。建议增加 JSON schema 校验，gen 完成后输出校验报告。
P2 CACHE 的字段没有标准化文档
CACHE 字典是事实上的数据结构，但没有 schema 定义。不同 collector 写入的字段名不一致（iwencai 的晋级率是 晋级率 还是 一进二晋级率，量比是百分数还是小数）。建议建立 CACHE_SCHEMA.md，每个字段注明类型、单位、来源、刷新频率。
P3 没有单元测试
整个项目没有测试文件。gen_dashboard_data.py 的解析逻辑（尤其是占位符 "—" 回退机制）如果有 bug，会影响所有组件。建议为 gen 的核心函数和 DataStore 的 merge 逻辑增加 pytest 测试。
