## 1. 产品概述

### 1.1 产品定位

弈沐资本数据看板是一套**模块化、可自由拼装的交易决策指挥台**。它将弈沐资本交易系统 v3.0 的规则体系、数据管线、决策流程外化为可视化组件，每个组件对应交易系统的一个独立决策维度或数据视图。

### 1.2 核心价值

| 痛点（当前） | 解决方案（本产品） |
|------------|-----------------|
| 单一 HTML 文件 1081 行，模块耦合 | 16 个独立 Widget，松耦合，可单独开发/测试/替换 |
| 布局固定，不同时段看同一套 | 自由拖拽缩放，4 套预设一键切换（盘前/W1/W2/复盘） |
| 数据逻辑混在渲染代码里 | DataStore 统一管理，组件只订阅自己需要的数据路径 |
| 无法按需组合（连板日不需要趋势池） | 右键菜单添加/删除组件，看什么加什么 |
| 数据来源不透明 | 每个数字可追溯到 SSOT（复盘笔记/iwencai/手工录入） |

### 1.3 设计原则

1. **交易模式外化**：每个组件名直接对应交易系统概念（竞价5维、W1/W2、三层仓位），看板即模型
2. **数据溯源**：任何数字都能回答"从哪来、多久更新、谁负责"
3. **决策优先**：决策类组件（回答问题）排在数据类组件（展示数据）之前
4. **零构建**：双击 HTML 即开，CDN 引入 GridStack.js，不依赖 Node.js/npm
5. **渐进可用**：即使后端数据源全部不可用，EMBEDDED_DATA 兜底，看板不白屏

## 2. 用户与场景

### 2.1 用户画像

**唯一用户**：弈沐哥（杨弈沐），弈沐资本唯一交易决策者。

特征：
- A 股短线 + 趋势混合交易
- 每日流程：盘前准备(8:30-9:15) → 竞价(9:25) → W1早盘(9:30-10:00) → 盘中观察(10:00-14:00) → W2尾盘(14:00-14:45) → 收盘复盘
- 数据输入方式：复盘笔记（稳米生成）、iwencai API 轮询（自动）、同花顺 APP 手工录入（15 字段）
- 技术环境：Mac 本地，Chrome 浏览器，双击 HTML 打开

### 2.2 使用场景

| 场景 | 时段 | 核心需求 | 推荐预设 |
|------|------|---------|---------|
| 盘前准备 | 8:30-9:15 | 看昨日收盘数据 + 风格检测结果 + 三层仓位计算 | `pre-market` |
| 竞价判断 | 9:25 | 竞价5维面板 + 高潮保护 | `pre-market`（滚动到竞价区） |
| W1 追涨 | 9:30-10:00 | 连板池 + W1早盘确认 + 情绪KPI | `w1-chase` |
| 盘中观察 | 10:00-13:00 | 板块热力 + 上证15min量价 + 市场全景 | `w1-chase`（自由调整） |
| W2 低吸 | 14:00-14:45 | 趋势池 + W2低吸条件 + 板块热力 | `w2-dip` |
| 收盘复盘 | 15:00后 | 全部数据回顾 + 报数面板录入 | `closing-review` |

### 2.3 用户故事

- **US1**：盘前 8:30 打开看板 → 1 秒看到风格分数 + 总仓位上限 + 昨日情绪基线 → 心里有数今天做什么
- **US2**：9:25 竞价结束 → 竞价5维全绿（4/5 方向确认）→ 按 `w1-chase` 预设一键切换到 W1 布局 → 连板池就位
- **US3**：盘中觉得板块热力太小 → 拖拽右下角放大到 12×6 → 8 板块一览无余
- **US4**：14:00 转 W2 → 切 `w2-dip` 预设 → 趋势池 + W2 条件就位 → 连板池自动隐藏
- **US5**：收盘复盘 → 切 `closing-review` → 报数面板展开 → 填 15 字段 → 刷新 → 数据存入 localStorage

### 4.2 DataStore 设计

```javascript
// store.js — 单一数据中枢
const DataStore = {
  // === 数据池 ===
  baseData: null,       // dashboard_data.json（Layer 1）
  liveData: null,       // dashboard_live.json（Layer 2）
  manualData: {},       // localStorage dash_inputs（Layer 3）
  merged: null,         // mergeData() 三层合并结果
  fallback: EMBEDDED_DATA, // Layer 0 兜底

  // === 刷新层级 ===
  tiers: {
    tick:    { interval: 5000,   sources: ['live_index'],           label: '5秒' },
    fast:    { interval: 30000,  sources: ['live_sectors'],          label: '30秒' },
    slow:    { interval: 300000, sources: ['上证15min', 'market'],   label: '5分钟' },
    manual:  { interval: null,   sources: ['sentiment', 'decision'], label: '手工' },
    daily:   { interval: null,   sources: ['style', 'sectors'],      label: '每日' },
  },

  // === 订阅中心 ===
  // subscribers[dataPath] = [callback1, callback2, ...]
  subscribers: {},

  // === 核心方法 ===
  get(path),                  // 读数据，支持点号路径 'sentiment.情绪值'
  subscribe(paths, callback), // 订阅数据路径变化，返回 unsubscribe 函数
  refresh(tier),              // 按层级拉取数据
  merge(),                    // 三层合并（复用 live-dashboard.html mergeData 逻辑）
  getSSOT(path),              // 返回数据溯源信息 {source, frequency, owner}

  // === 连接状态 ===
  connectionStatus: 'polling', // 'live'|'polling'|'dead'
};
```

### 6.3 组件生命周期

```
register → instantiate → mount → (resize/refresh repeat) → unmount

1. register: WidgetRegistry 注册组件 class 和元数据
2. instantiate: 用户右键添加 / 预设加载 → new WidgetClass(config)
3. mount: GridStack 创建 DOM 容器 → widget.render(data) → DOM 填充
          → widget.onMount(container) → 绑定事件、启动定时器
          → DataStore.subscribe(paths, widget.render)
4. refresh: 定时器触发 / 用户点击刷新 / DataStore 通知 → widget.render(newData)
5. resize: GridStack 检测尺寸变化 → widget.onResize(w, h) → 自适应渲染
6. unmount: 用户删除组件 → 取消订阅 → 清除定时器 → GridStack 移除 DOM
```

| 系统 | 阴影层级 | 设计哲学 |
|------|---------|---------|
| **PRD 当前** | **2 级** | 通用 |
| **Linear** | **8 级** | 暗色背景靠亮度分层而非阴影 |
| **Sentry** | **5 级** | 紫调环境光 + 内凹按钮 |
| **Kraken** | 2 级但够用 | 亮色背景仅需微妙阴影 |

**建议补充 6 级阴影**：
```css
--shadow-flat: none;                                /* 画布层 */
--shadow-card: 0 1px 0px rgba(0,0,0,0.4);          /* 组件默认（单线阴影） */
--shadow-elevated: 0 4px 12px rgba(0,0,0,0.5);     /* 悬停/选中 */
--shadow-drag: 0 8px 24px rgba(0,0,0,0.6);          /* 拖拽中 */
--shadow-modal: 0 0 0 1px rgba(255,255,255,0.08),   /* 弹窗 */
                0 24px 48px rgba(0,0,0,0.7);
--shadow-glow-info: 0 0 12px rgba(92,156,230,0.12); /* 信息类微光（PRD已有） */
```

**暗色底阴影铁律**：阴影不应是全黑 `rgba(0,0,0,x)`，应带色温——`rgba(10,14,20,0.6)` 偏蓝黑而非灰，避免「浮灰感」。

---

##### 1.2 缺少「5秒规则」上层设计约束（§5 — Blocker）

这是 PRD §5 最大的概念缺失。

> **5 秒规则**（ChartsWatcher 2025、UXPin 等行业共识）：用户打开看板 5 秒内，必须能判断出今天的交易信号是好是坏。

以此约束反推盘前预设 `pre-market` 的现有布局：

| 现状 | 问题 | 建议 |
|------|------|------|
| W01 时段时间线占顶部 12×1 黄金位置 | W01 是纯展示工具组件，不是决策信息 | 压缩为 12×0.5 的细条条，或缩小列宽 |
| W02 风格检测卡（4×4）放在中间偏右 | 风格分数是「今天做什么模式」的最关键决策 | 提升为左上角 P0，让用户 5 秒内看到 |
| W04 市场全景（4×3）放在 W02 左侧 | 大盘数据次优于风格判定 | W04 和 W02 交换位置，或缩小 W04 |

**核心思路**：组件的排列优先级不是按「类型分组」，而是按「决策链」——风格检测最先看，其次风控和仓位，再次大盘和情绪。

---

##### 1.3 缺少完整交互状态定义（§5 — Important）

PRD §5.4 和 §5.1 只定义了组件的默认视觉样式和悬浮 tooltip。但看板有 6 个可交互元素（W16 报数面板 15 输入框 / 组件标题栏按钮 / 右键菜单 / 预设切换 / 全屏切换 / 键盘快捷键），缺少：

| 状态 | 需要定义什么 | 影响范围 |
|------|------------|---------|
| **hover** | 按钮、表格行、可交互卡片 | 全组件 |
| **active/press** | 点击时的瞬间反馈 | 所有按钮类元素 |
| **focus** | 键盘导航（W16 输入框） | 无障碍起点 |
| **disabled** | 数据过时/组件不可用 | 数据过时状态 |

**参考方案（Linear 风格，暗色背景）+2% 递进法**：
```css
/* 所有交互元素统一用背景透明度递进表示状态 */
--interactive-default: rgba(255,255,255,0.02);
--interactive-hover:   rgba(255,255,255,0.04);   /* +2% */
--interactive-active:  rgba(255,255,255,0.06);   /* +2% */
--interactive-disabled: rgba(255,255,255,0.01);   /* 几乎消失 */
```

看板 16 组件用 4 种字号，但**所有按钮/标签/表格行 hover 亮度统一增加 2%**，效果比色相变化更统一。

---

##### 1.4 字体栈缺少层级差异化（§5.2 — Important）

PRD 定义了 `--font-sans` 和 `--font-mono`，所有 5 种字号（28/22/13/12/10px）共用一套系统字体栈。

这是 Bloomberg Terminal 的做法——功能优先、颜值其次——但不是现代看板应该做的。

**对比参考**：

| 字号 | PRD 字体 | Linear | Sentry |
|------|---------|--------|--------|
| 28px Hero | 系统 sans | Inter 510 | Dammit Sans |
| 22px KPI | 系统 sans → **mono ✅ 正确** | Inter 510 | Rubik |
| 13px Header | 系统 sans | Inter 400 | Rubik |
| 12px Body | 系统 sans → **mono ✅ 正确** | Inter 400 | Rubik |
| 10px Label | 系统 sans | 大写 + letter-spacing | 大写 + 0.25px |

**建议**：
- KPI 数字（22px）和表格数据（12px）用 mono 字体 → **当前就是对的，保持**
- 10px Label 层应增加 uppercase + letter-spacing，不只是一个字号变量
```css
--fs-label: 10px;
--ls-label: 0.3px;          /* 新增 */
--tt-label: uppercase;       /* 新增：label 全部大写 */
```

**字体参考替换方案**（如果不满意系统字体栈的阅读体验）：
- sans → **Inter**（Google Fonts 免费，40MB 月活，99% 中文兼容）
- mono → **JetBrains Mono**（Google Fonts 免费，代码/数字阅读最优）

##### 1.5 色板缺少紫色系高亮色（§5.1 — Important）

PRD §5.1 定义了：红（涨）、绿（跌）、蓝（信息/通过）、橙（警告/待定）、红（危险/熔断）、紫（特殊/V反）。

16 个组件用左侧 3px 色条区分类型（决策/数据/风控/工具），但**缺少一个「非紧急但重要」的高亮色**。

场景示例：W1 确认通过，但连板池量能不够、需要关注但不是熔断——用红色太重，用蓝色太柔和，用新颜色「紫色」正好。

**建议新增**：
```css
--accent-purple: #7c4dff;           /* 用于重点提醒但不紧急的场景 */
--accent-purple-bg: rgba(124,77,255,0.10);
```

**参考**：Sentry 的 Lime Green（`#c2ef4e`）只在关键场景出现，既不绑方向色也不绑语义色，独立存在——这是专业设计系统的做法。

---

##### 1.6 缺少数据新鲜度指示器（§5.3 — Nice-to-have）

每个组件定义了「数据来自 X 源，每 Y 秒刷新」，但**组件本身没有任何视觉元素告诉用户「这个数据是否过时」**。

**建议在组件标题栏右侧统一增加时间戳**：
```css
/* 组件标题栏右侧，10px mono，text-secondary */
.data-timestamp {
  font: 10px var(--font-mono);
  color: var(--text-secondary);
  font-variant-numeric: tabular-nums;
}
/* 超过 2 倍刷新间隔未更新时变色 */
.data-timestamp--stale {
  color: var(--warn);
}
```

**时间戳格式示例**：`[12:34:22]`

---

##### 1.7 mono 字体数字对齐需补充 lining-nums（§5.2 — Nice-to-have）

PRD 提到 `font-variant-numeric: tabular-nums`，正确。但建议补充：
```css
font-variant-numeric: tabular-nums lining-nums;
```
`lining-nums` 确保不同字重下的数字高度统一对齐，避免表格内 12px 和 16px 数字错位。

---

##### 1.8 缺少分屏断点（§5.5 — Nice-to-have）

PRD 定义 2560/1920/1280/768/<768 四个断点，但**没有考虑分屏场景**。

实际使用场景：同花顺（左半屏）+ 看板（右半屏）= 约 960px。
此时看板用 8 列还是 4 列？GridStack 如何降级？

**建议补充**：
| 断点 | 列数 | 场景 |
|------|------|------|
| 1200px | 10 列 | 窄屏桌面 |
| **960px** | **8 列** | **分屏/侧边栏场景（同花顺+看板）** |

---

##### 1.9 W11 量价柱方向需确认（§5.3 W11 规格 — Nice-to-have）

黑米评审已提出：PRD 定义「涨=红、跌=绿，量比>1 向下延伸，量比<1 向上延伸」——柱体方向与 A 股常见量价图习惯相反（通常量大柱高/长）。

**建议**：如果这是弈沐哥的个人偏好设计，在 PRD 里显式标注「此为非标准方向，弈沐哥个人偏好」，避免黑米/稳米实施时以为笔误。

#### 二、技术栈选型评估

> 评估对象：GridStack.js v12 CDN + 原生 ES6 Class（YiMuWidget 基类）+ DataStore 订阅-发布。

##### 2.1 技术栈评估（6 维度）

| 维度 | 评分 | 说明 |
|------|------|------|
| 零构建约束 | ✅ **完美满足** | CDN 引入 GridStack，双击 HTML 即开 |
| 16 组件规模 | ✅ **够用** | 全都是「读数据→渲染」，非复杂交互应用 |
| 拖拽+缩放需求 | ✅ **GridStack 原生支持** | 框架中最好选择 |
| 布局持久化 | ✅ **grid.save()/load() API 完善** | 无需手写 JSON |
| 长期可维护性 | 🟠 **够用，但有改进空间** | 见下文 2.2、2.3 |
| 组件间通信扩展性 | 🟠 **当前够，未来需注意** | 见下文 2.4 |

**结论**：在此场景下，GridStack + 原生 ES6 是正确的选择。React/Vue/Svelte 等 SPA 框架因「需 build 后才能打开」直接被「零构建」约束淘汰，根本不在候选范围内。

---

##### 2.2 建议升级方向：从 YiMuWidget 基类 → 原生 Custom Elements v1

PRD 规划用 `widget-base.js` 提供 YiMuWidget 基类，16 个组件通过 ES6 Class 继承实现。但既然已经在封装组件体系，**建议直接用 Custom Elements v1（Web Components 标准）**，成本极低，收益明确：

| 维度 | YiMuWidget 基类 | Custom Elements v1 |
|------|----------------|-------------------|
| DOM 封装 | 手动 className 管理 | ✅ Shadow DOM 自动隔离 |
| 样式隔离 | ❌ 全局 CSS，起名需规范 | ✅ 每个组件独立作用域 |
| 生命周期 | 3 个自定义方法 | ✅ connectedCallback / disconnectedCallback 等标准化 |
| 浏览器兼容 | ✅ 全部 | ✅ 2026 年全部主流浏览器支持 |
| 标签语义化 | 无（手动 DOM 操作） | `<ym-widget type="sentiment-dash">` 原生 HTML |

**示例代码**（仅为说明概念，不直接替换 PRD 技术方案）：
```javascript
class YiMuWidget extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
  }
  connectedCallback() {
    this.render(this.dataset.widgetId);
  }
  render(widgetId) {
    // 在 this.shadowRoot 中操作，样式自动隔离
  }
}
customElements.define('ym-widget', YiMuWidget);
```

**注意**：如果 16 个组件全用 Shadow DOM，`theme.css` 中的 CSS 变量默认不会穿透到 Shadow DOM。需要在每个组件的 constructor 中手动注入——通过 `getComputedStyle(document.documentElement).getPropertyValue('--up')` 获取并写入。

---

##### 2.3 GridStack 版本锁定提醒

PRD §6.1 建议注明 `GridStack.js@12.x`，但未锁定 minor 版本。

GridStack v12 与 v11/v10 存在 breaking changes（如 `animate: true` 默认行为改变、部分 API 签名变更）。

**建议**：在 CDN URL 中锁定具体版本，而非用 `dist/gridstack-all.js` 指向最新版。避免未来 GridStack 更新引入 breaking changes 导致看板功能异常。

---

##### 2.4 组件间通信复杂度边界

当前 16 个组件各自独立，数据通过 DataStore 统一管理。这种模式在以下场景会达到边界：

| 场景 | 当前方案 | 是否需要换方案 |
|------|---------|-------------|
| W12 连板池选中标的，W10 板块热力高亮对应板块 | ⚠️ 需要 EventBus 或 DataStore 加强 | 原生 Event 够用 |
| W08 判定结果反过来彩显 W12 连板池标的颜色 | 🟠 派生数据字段 | 原生够，DataStore 加 getDerived() |
| 未来接入 Dify 作为数据中间层 | 🟠 需要 dataAdapter 抽象层 | 原生够 |
| 未来接入 WebSocket 实时推送 | ⚠️ 换 SSE 替换 setInterval polling | 原生够 |
| 未来看板嵌入同花顺/飞书 iframe | 🟠 Custom Elements 更适合嵌入式场景 | WC 本身原生 |

**结论**：如果看板始终停留在当前规模，当前方案永远够用。如果未来需要组件间深度联动，应在 Phase 1 提前做好 DataStore 的事件机制设计。

---

##### 2.5 mergeData() 第三层 DOM → DataStore.manualData 接口变更提醒（重申稳米 Blocker #3）

当前 `mergeData()` 的第三层通过 `document.getElementById('in_xxx')` 直接读 DOM 输入框的值。迁移到 store.js 后：
- W16 报数面板的输入事件应驱动写入 `DataStore.manualData`
- `mergeData()` 改为读 `DataStore.manualData` 而非 DOM
- 这是整个迁移中最大的接口变更

**建议**：Phase 1 启动时，稳米先输出 DataStore API 文档（明确 subscribe() / publish() / manualData.set() 三个核心接口的签名），黑米再开始组件开发。

---

##### 2.6 技术栈评估总结

| 角度 | 结论 |
|------|------|
| GridStack + 原生 ES6 是否适合当前场景 | ✅ **可选正确**，零构建约束下最优解 |
| React 是否更好 | ❌ 淘汰理由：不能双击 HTML 打开 |
| YiMuWidget 基类 | 🟠 **建议升级为 Custom Elements v1**，Shadow DOM 隔离收益大、成本极低 |
| 长期来看是否需要换框架 | ❌ 不换。保持原生足够。注意组件间通信复杂度边界 |
