## 三、原计划需要修正的问题

### B0 - 阻断：HTTP 请求泄漏 SQLite 连接

**证据：** `scripts/db.py:21-31` 把 SQLite 连接保存在线程本地；`ThreadingHTTPServer` 每个请求创建处理线程；代码没有正常 request 结束后的 `close`。运行中的 bridge 已持有大量 `pnl.db`/`pnl.db-wal` 句柄，随后 `/api/account/state` 连 JSON 文件都无法打开。

**影响：** 资产、PnL、健康检查和 AI 快照都会随机失败；任何功能验收均失去意义。

**修正：** Gate 0 首任务增加 `close_conn()`/请求收尾释放与并发压力回归；WAL 是否保留须以压力测试和异常重启测试为依据，不能仅凭事故叙述切换日志模式。

### B1 - 阻断：SSOT 测试会写真实日结文件

**证据：** `tests/test_account_ssot.py:255-258,486-489` 调用 `generate_closing_anchor()` 时只替换临时数据库；`scripts/account_ssot.py:273-318` 无参数地写 `ROOT/data/pnl_history.json`。

**影响：** 跑测试可覆盖真实资产元数据，导致第二天锚点、收益与验收数字被测试数据污染。

**修正：** Gate 0 将日结文件路径注入化，所有日结测试使用临时路径；增加“跑测试后 `data/` 无 diff”验收。

### B2 - 阻断：纠错 API 被实现成带副作用的 GET

**证据：** `scripts/bridge.py:592-622` 的 `/api/account/correct` 在 `do_GET()` 内读取 body 并插入冲销流水；`do_POST()` (`scripts/bridge.py:738-1028`) 没有该路由。

**影响：** 前端或客户端无法按命令语义可靠调用；GET 产生交易写入也违反可审计接口边界。

**修正：** 仅保留 `POST /api/account/correct`，GET 返回 `405`；加 HTTP 级测试确认重复/错误调用不会修改账本。

### B3 - 高：环境安装与迁移任务不完整

**证据：** README 只声明“无 Node/npm 依赖”，未声明 Python 运行依赖；`scripts/collectors/quotes.py:12`、`iwencai_poll.py:9`、`market_data.py:9`、`snapshot_auction.py:16`、`style_detect.py:27` 仍写死 `/Users/YouMing/...`；本机未安装 `pytest`。

**影响：** 新机启动和完整测试不可复现。

**修正：** 使用项目虚拟环境和依赖清单，不再要求往系统 Python 使用 `--break-system-packages`；活动脚本统一解析 `ym_stock_data` 的安装包或可配置开发路径。

### B4 - 高：规则不是单一口径，也不是实时口径

**证据：**

- `scripts/gen_dashboard_data.py:638-704` 只在每日 gen 时生成部分 `style.实际执行`。
- W03 仍自行从每日 `risk` 判断熔断（`widgets/position-calc.js:20-29`），W08/W09 另写门槛逻辑。
- `store.js:549` 明确标注 `risk.熔断触发` 来源仍为每日复盘 frontmatter。
- `LLM_RULES.md:53-59` 规定 `<40` 上限为 `20%`，而 `_compute_total_cap()` (`scripts/gen_dashboard_data.py:627-636`) 及测试给 `<20` 返回 `10%`，文本与机器已有冲突。

**影响：** 盘中亏损触发熔断时，组件和 AI 可能仍显示可开仓；审核无法证明规则唯一。

**修正：** 后端新增纯函数实时规则状态，账户 SSOT 当日 PnL 与实时情绪是输入，`/api/live/quotes` 输出 `rule_state`，组件与 AI 只消费这个状态。

### B5 - 高：AI 校验器与其输入快照字段契约不匹配

**证据：** 快照构造返回 `趋势池`/`板块` 及字段 `标的`（`scripts/bridge.py:419-501`），校验器却读取 `趋势自选`/`sectors` 和 `name`/`dist_to_ma10_60m`（`scripts/bridge.py:181-261`）。LLM 仍依赖 `[TEXT]` / `[SIGNALS]` 字符串拆分，并且手动、自动流程各复制一套解析逻辑（`scripts/bridge.py:935-1011,1229-1278`）。

**影响：** “verified” 不是可证明结论，新增 schema 前必须先修字段契约与共用解析入口。

**修正：** Gate 1 中让 AI 信号验证直接消费 `rule_state` 和规范化标的键，解析/验证/持久化共用一个函数。

### B6 - 中高：DataStore 收口任务需重写

**证据：**

- W05 仍在每次 render 直接 fetch 文件（`widgets/sentiment-dash.js:9-20`）。
- DataStore 虽读取 `sentiment_auto.json`，却写为 `_sentiment_auto` 后再次 `merge()`，未形成 registry 声明的 `sentiment_nodes` 数据域（`store.js:371-383`）。
- W06 直接读取 `auction_snapshot.json`（`widgets/auction-5d.js`）；当前 DataStore 没有 auction 数据源。
- W11/W12/W13/W16 使用裸 `addEventListener()` 而非基类 `_on()`（例如 `widgets/volume-bars.js:153-171`、`widgets/lianban-pool.js:92-101`）。

**影响：** 直接要求 widget “改订阅”会没有可订阅数据；必须先补 DataStore 数据域，再改组件。裸监听在静态审查中只能确认生命周期约定不一致，是否存在重复响应须由挂载/卸载测试证明。

**修正：** Gate 2 先定义 `sentiment_nodes`、`auction_snapshot` 数据适配器及刷新频率，再迁移 widget。

### B7 - 中高：SSOT 前端仍存在零值误判

**证据：** `widgets/position-calc.js:38-54`、`widgets/risk-panel.js:47-53`、`widgets/positions.js:97-102` 用 `parseFloat(ssotValue) || fallback`。

**影响：** 合法 `cash=0` 或 `mv=0` 会回退到旧基线或推算值，账户展示再次偏离 SSOT。

**修正：** Gate 0 按“字段存在且可解析”而非 truthy 判断 SSOT 数值，补现金为零、空仓为零的前端验收用例。

### B8 - 中：已有确定性小错应随首批前端修复处理

| 问题 | 证据 | 修正 |
| --- | --- | --- |
| W09 `"不好"` 可匹配“好” | `widgets/w2-check.js:50` | 使用明确允许枚举 |
| W08 的 W1 时段判断把 09:00-09:29 也视为 W1 | `widgets/w1-check.js:40-43` | 仅 `09:30-10:00` 为真 |
| 竞价“10:00 备份快照”会改变定格语义 | 计划原文 P1-E | 仅当 09:28 快照缺失/无效时做补抓，并标记 `source=catchup` |

## 四、目标架构边界

### 4.1 资产状态不变更边界

`account_baselines + trade_records + fund_events + live_quotes -> account_state`

- `account_state` 继续是资产/持仓/PnL 唯一权威。
- 规则、健康中心、复盘只读取资产结果，不反写现金或持仓。
- `dashboard_data.json.positions` 仍可作为展示镜像和兼容降级，不可成为盘中计算源。

### 4.2 实时规则状态新边界

`account_state + sentiment/live_index + baseline style + time -> rule_state`

推荐由 `scripts/rule_engine.py` 返回以下稳定对象，并由 `/api/live/quotes` 同批返回：

```json
{
  "evaluated_at": "2026-05-26T14:10:00+08:00",
  "source_freshness": {"account": "live", "sentiment": "delayed"},
  "blocked": true,
  "blocks": [{"code": "DAY_STOP", "label": "单日熔断", "evidence": "-3.12% <= -3%"}],
  "caps": {"total_pct": 0, "lianban_pct": 0, "trend_pct": 0, "first_order_pct": 0},
  "windows": {
    "W1": {"allowed": false, "reasons": ["DAY_STOP"]},
    "W2": {"allowed": false, "reasons": ["DAY_STOP"]}
  },
  "alerts": []
}
```

- W03 展示 `caps`；W08/W09 展示 `windows`；W14 展示 `blocks/alerts`。
- AI 可解释规则，但任何 BUY 只有 `rule_state.windows[window].allowed=true` 且标的条件通过后才可标记 verified。
- `LLM_RULES.md` 是人读说明，必须与规则测试中的阈值保持同步，不再作为机器执行入口。

### 4.3 健康状态新边界

`runtime checks + data freshness + account valuation_complete + db integrity/status -> /api/health`

- 使用已经存在的 `_updated` / `_freshness`，不创建并行的 `_fetch_time` 字段。
- `ymwm_report.json` 可作为运维报告附件，不能替代当前运行态检查。
- 健康总状态必须能阻止“数据失效但仍给买入提示”的界面展示。

### 4.4 复盘数据新边界

`trade_records` 仍为成交事实，新增的规则结果和市场快照只是成交时上下文：

- 可在流水扩展 `decision_context_json`、`rule_state_json`、`review_note`、`outcome_json` 等非资产字段。
- 不创建第二套会修改数量/现金的“操作记录”表。
- 月/季度归因统计必须从已确认的成交上下文推导。
