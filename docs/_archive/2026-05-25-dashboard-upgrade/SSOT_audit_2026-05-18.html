5. 问题清单

按严重程度排序 · 共 16 项

严重 · 数据错误或 null

#1 sentiment_auto.json 情绪值始终为 null
严重
文件：collectors/sentiment_snapshot.py:50影响：30min 快照无核心指标
代码第 50 行 "情绪值": iwencai.get("情绪值")——但 iwencai CACHE 中不存在 "情绪值" 键。iwencai_poll.py 写入的键是 封板率/炸板率/晋级率 等，从未写入 情绪值。情绪值由 store.js 前端从 T3 涨跌家数比计算。一个月来全部快照 情绪值=null。
修复：改为从 CACHE["live_index"] 计算：上涨家数 / (上涨家数+下跌家数) × 100，与 store.js T3 逻辑一致。
#2 sentiment_auto.json 炸板率 72–74% vs 真实值 29.82%
严重
sentiment_snapshot.py:55偏差：+42–44pp
复盘笔记炸板率 29.82%（封板率 70.18%，两者合计 100%）。但 sentiment_auto 记录炸板率 0.72–0.74（72–74%），与封板率 0.69–0.72 非常接近。怀疑 iwencai API 返回的“炸板率”字段定义为 已炸板数÷总涨停数，而非 炸板数÷曾涨停数，导致数值偏大。也可能是字段解读反转。
修复：验证 iwencai API 炸板率字段定义。如确认值不对，改为从封板率推算：炸板率 = 1 − 封板率。
#3 P&L NAV 硬编码 = 1.0，sh/sz/cy_pct 恒为 0，日内追踪全不可用
严重
collectors/quotes.py log_pnl_snapshot()影响：W22 曲线 + 风控联动
log_pnl_snapshot() 写入 pnl.db 时：nav=1.0 硬编码，sh_pct/sz_pct/cy_pct 全部 = 0。导致盘中 NAV 恒为 1.0，无法计算真正的 TWR NAV。W22 收益曲线日内数据不可用。pnl_history.json 的 intraday_histories 空字典——盘中 P&L 追踪全线瘫痪。
修复：接入真实账户数据：从 pnl_history.json meta 取 last_twr_nav，从 W16 localStorage 取当前总资产，计算 NAV = 当前总资产 / 初始入金。sh/sz/cy_pct 从 live_index 实时获取。

高 · 分歧 >20% 或结构性缺失

#4 连板风险值 s_auto = 0.77 vs 复盘 = 0.27 — 差值 0.50
高
iwencai_poll.py Q5：1−晋级率 vs 复盘笔记公式
iwencai 公式：连板风险值 = 1 − 晋级率 = 1 − 0.23 = 0.77。复盘笔记 = 0.27。两者使用完全不同的计算公式。0.27 可能从涨停收益/炸板收益等多因子综合计算，而非简单 1−晋级率。
修复：确认复盘笔记 0.27 的计算逻辑，统一 iwencai_poll.py 的风险值公式。
#5 dashboard_data.json 7 个关键字段 = "待收盘"
高
dashboard_data.json market + sentiment 域
涨停家数/跌停家数/炸板率/封板率/晋级率及三分层晋级率 全部为 "待收盘"。gen_dashboard_data.py 在 15:10 运行时，稳米尚未完成复盘笔记收盘段填写。
修复：gen 脚本增加回退逻辑——frontmatter 为空时解析五节点表格收盘行；或将 gen_baseline_1510 推迟到 16:30。
#6 sentiment_auto 涨停/跌停家数 = 0 或 null
高
sentiment_snapshot.py:51-52
"涨停家数": breadth.get("涨停") or live_index.get("涨停")——live_index 无 "涨停" 键。breadth 有 "涨停"/"跌停" 键但部分时段为空。收盘快照 涨停家数=0 是明显错误。
修复：仅从 breadth 读取，不 fallback 到不存在的 live_index.涨停。breadth 为空时标记 null 并记日志。
#7 整体晋级率 s_auto = 23.06% vs 复盘 = 16.67% — 差值 6.4pp
高
iwencai Q2 聚合 vs 分层加权
iwencai Q2 "涨停晋级率 连板股数" 返回全市场聚合值。复盘笔记使用分层统计（一进二/二进三/三进四各层晋级率分别计算）。两者口径不同。
修复：确认复盘 16.67% 的计算口径，iwencai_poll 改为分层查询或与复盘公式对齐。
#8 pools.json (7 标的) vs dashboard_data.json (6 标的) — lianban_pool 来源不同
高
pools ← 附录A（定稿）· dash ← 数据附录（中稿）
pools.json 从 附录A 次d日盘前速查 解析（含蒙娜丽莎共 7 标的）。dashboard_data.json 从 数据附录 解析（6 标的，缺蒙娜丽莎）。附录A 是定稿版本。
修复：gen_dashboard_data.py 的 lianban_pool 优先从附录A 解析（与 pools.json 同源），数据附录回退。

审计结论

数据管线整体架构合理——APScheduler 统一调度 + CACHE 内存层 + store.js 三层合并的设计方向正确。核心问题集中在三个层面：

  1. sentiment_auto.json 数据质量——情绪值 null + 炸板率错误 + 涨停家数 0，三条都是代码层 bug，可快速修复
  2. 多源定义不一致——晋级率/连板风险值的计算口径在 iwencai 和复盘笔记间不同，需要统一公式
  3. 时序问题——gen_baseline 运行过早 + is_trading_time 四模块不一致，导致边界时段数据缺失、基线数据存午盘值
