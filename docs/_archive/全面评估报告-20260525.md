# 弈沐资本数据看板 v2.5 全面评估报告

> 日期：2026-05-25 | 评估范围：22 组件 + 后端管线 + AI 系统 + UI/UX + 交易决策支持

---

## 摘要

这个看板的架构设计相当扎实——三层数据合并、SSOT 审计记录、Widget 生命周期管理、CSS 变量系统，都是正确的工程选择。最难得的是它真正服务于你个人的交易体系，不是通用模板。LLM_RULES.md 把规则显式化了，AI 不是黑盒而是被约束的助手。

最值得优先投入的方向有两个：
1. **补上信号到执行的闭环** — W08/W09 的买入信号应该一键录入 W15
2. **信息降噪** — 精简模式 + 数据新鲜度统一化 + W20 持仓异动主动提醒

## 一、数据管线 — 可靠性与盲区

### 做得好的
- CACHE 热启动（`cache_dump.json`）保证 bridge 重启后不白屏
- `atomic_write_json` + FileLock 防止多进程写入损坏
- 竞价快照选在 9:28（给 iwencai 留足处理时间）
- 三层 PnL 保护机制（gen 不覆盖实时持仓）
- 成交额对比用 `update()` 而非赋值——避免了昨天数据被抹的问题

### 存在的问题

**P0 — iwencai 数据质量隐患**。10 分钟轮询一次，但 iwencai 的 pywencai fallback 是同步阻塞的，每次 poll 要跑 8 个查询。若 OpenAPI 超限或 pywencai 报错，整个 iwencai 数据域会静默退化为旧值，前端没有任何「数据过期」警告。建议在 `CACHE["iwencai"]` 增加一个 `_fetch_time` 字段，前端组件据此显示「数据已过时 N 分钟」警告。

**P1 — 竞价快照只跑一次**。`snapshot_auction.py` 只在 9:28 执行一次，如果当天 bridge 重启，竞价快照永远是 9:28 的数据。建议增加一个 10:00 备份快照。

**P1 — `yesterday_compare` 数据脆弱**。昨日成交额对比依赖 PyTDX 的 15 分钟 K 线数据，但 PyTDX 连接在行情波动时容易抖动。当前 `collect_yesterday_compare` 没有独立日志，如果这个数据丢了，W04 成交额对比就永久空白。

**P2 — `sentiment_auto.json` 是.append 操作**。每次快照追加到文件末尾，若当机时文件写入一半，可能损坏 JSON 结构导致 W05 读取崩溃。建议换成 append-only 格式（每行一个 JSON），或者写临时文件再 rename。

## 二、22 组件质量

### 高质量组件（7 个）
W17（今日操作）、W19（午盘复核）、W18（锚定）、W07（高潮守护）代码简洁、错误处理完善。W15、W04、W22 功能最丰富但复杂度高。

### 存在问题的组件

**P0 — W05、W06 数据源不规范**：不通过 DataStore 订阅，直接 `fetch()` 文件，破坏 SSOT 架构。

**P0 — W12、W13 代码重复**：两个组件近 100 行几乎完全相同，维护成本翻倍。

**P1 — W11、W12、W13、W16 事件监听器泄漏**：`addEventListener` 没有通过 `_domListeners` 追踪，组件销毁时监听器残留。

**P1 — W14 缺少 `updateTimestamp()`**：风控面板 W14 在 `render()` 末尾没有调用 `this.updateTimestamp()`，导致数据新鲜度指示器始终显示灰色。

**P2 — W08、W09 的 `profitFx.indexOf('好') >= 0` 逻辑**：`"不好"` 会被错误匹配为正收益。

**P2 — W10、W21 每次 render 都发 fetch**：没有 `_loading` 状态锁。

### 语义不一致

W12 的「追」用红色，W13 的「买入」用绿色。两者都是买入信号但颜色相反，容易混淆。建议统一：买入 = `up`（红）。

## 三、AI/LLM 系统

### 当前优势
- 14 分钟自动研判，后台运行，浏览器关了也跑
- ReAct 信号验证层，防止幻觉信号
- 3 轮对话记忆，W20 监控卡片 + 浮动聊天框双入口
- DeepSeek V4-Flash 成本可控

### 深度问题

**P1 — LLM 输出格式依赖标记词**。后端用 `[TEXT]`/`[SIGNALS]` 字符串分割来解析输出，模型格式稍变就静默失败。当前没有对解析结果的 schema 校验。

**P1 — ReAct 验证过于宽松**。对每个信号只检查基础条件，但不验证信号与当前情绪区间的匹配度。例如在冰点（情绪 <20%）时，模型输出 BUY 信号仍会被标记为 verified。

**P2 — 系统 Prompt 无版本控制**。`LLM_RULES.md` 是纯文本，每次修改即时生效，没有版本记录。

**P2 — 手动/自动模式共享同一个流**。如果自动研判出错（如 iwencai 数据异常），手动问答也会受影响。

**P3 — 对话历史只存今天**。历史对话没有长期保存。

## 四、UI/UX 设计 — 暖砚风格

### 做得好的
- CSS 变量系统（54 个变量）覆盖完整
- `tabular-nums lining-nums` 数字等宽
- 红涨绿跌 + 符号双保险
- Widget 分类色条视觉清晰
- GridStack 可拖拽布局

### 存在的问题

**P1 — W20 浮动聊天框层级冲突风险**。`z-index: 3000` 硬编码，与其他浮层可能冲突。

**P1 — 没有暗色模式**。长时间盯盘的投资者会希望暗色主题。

**P2 — 响应式布局缺失**。GridStack 配置固定 `column: 12`，笔记本（1366×768）上组件过于拥挤。

**P2 — 组件刷新时无骨架屏/过渡**。数据刷新时直接替换，没有淡入淡出。

**P3 — 全局快捷键没有冲突检测**。

## 五、交易决策支持

### 当前链路
```
LLM_RULES.md (规则) → W08/W09 (规则执行检查) → W15 (操作录入) → W17 (今日操作展示) → W22 (PnL闭环)
```

### 缺失的环节

**P1 — 缺少「信号 → 操作」的确认流程**。W08/W09 显示「买入/等待/降级」信号，但信号到 W15 录入之间是手动操作。建议增加「录入操作」快捷入口。

**P1 — 仓位计算 W03 依赖 gen 数据**。熔断触发时 W03 不会自动更新上限。

**P2 — W02 风格检测是每日一次静态值**。盘中风格可能改变，但 W02 无法感知。

**P2 — 没有止损提醒的实际触发**。W14 可以显示持仓成本和现价，但没有主动报警。

**P3 — 冰点/双冰检测是静态的**。应该在 gen 阶段自动化。

## 六、个人投资者场景适配

### 需要精简的

**P1 — 22 个组件过多了**。实际盘中操作只需要盯 5-8 个核心组件：W04、W07、W08/W09、W15、W22。建议增加「精简模式」开关。

**P2 — W21 梯队面板太复杂**。571 行代码，信息量过大，盘中反而分散注意力。建议拆分为「盘中快速查看」和「盘后复盘」两个视图。

**P2 — 数据新鲜度显示不统一**。部分组件没有 `data-timestamp` 指示器。

### 需要增强的

**P1 — 增加「盘前预案」功能**。在 W16 增加一个「今日预案」文本区，记录开盘前的核心判断。

**P1 — 成交额感知的量化阈值**。建议增加「量能信号」指示（放大/正常/萎缩），直接显示在 W04 成交额旁边。

**P2 — 持仓联动到 LLM 研判**。如果持仓中有股票出现异常波动，应该主动触发专项研判，而不是等 15 分钟。

**P2 — 增加交易日志的「原因-结果」对照**。盘后自动计算每个操作的实际效果，作为 AI 复盘的学习素材。

## 七、架构与代码质量

### 做得好
- `YiMuWidget` 基类设计合理，生命周期清晰
- DataStore 的三层合并架构是正确的抽象
- SSOT 审计已识别并记录了关键数据域
- CSS 变量系统避免了样式碎片化

### 需要改进

**P1 — 组件间通信机制缺失**。跨组件协调靠 `window._llmChat` 这样的全局 hack。建议在 `store.js` 增加一个事件总线。

**P1 — `_domListeners` 追踪不完整**。W11/W12/W13/W16 都没有使用它，建议在基类增加 lint 提示。

**P2 — gen_dashboard_data.py 是单点依赖**。格式没有 schema 校验，静默失败风险高。

**P2 — CACHE 的字段没有标准化文档**。iwencai 数据小数 vs 百分数格式不一致的问题始终是隐患。

**P3 — 没有单元测试**。
