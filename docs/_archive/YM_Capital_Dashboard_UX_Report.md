## 2. 架构层面评估

### 2.1 ✅ 优势

- **零构建纯前端**：打开即用，file:// 协议也兼容，部署零成本
- **错误隔离**：YiMuWidget 的 `_renderBody()` 用 try-catch 包裹，单个组件崩溃不影响整体
- **SSOT 溯源机制**：`DataStore.getSSOT(path)` 可追溯每个数据字段的来源
- **兜底策略**：EMBEDDED_DATA 确保 file:// 不白屏
- **快捷键支持**：R 刷新 / P 跳转报数 / Ctrl+S 保存 / A 菜单
- **组件独立生命周期**：mount/unmount 自动管理定时器清理和订阅释放

### 2.2 ❌ 架构级优化点

#### 2.2.1 全量 `innerHTML` 赋值 — 性能瓶颈

**问题**：每个 widget 的 `render()` 都是 `body.innerHTML = html`。当 5s tick 触发全局 notifyAll，所有 tick 级别组件（W04/W08/W09/W14/W15/W18/W12/W13/W21）同时全量重绘。22 个组件中有 15 个属于 tick/fast/realtime 层级。

**影响**：
- 高频 tick 下 DOM 频繁重建 → 闪烁 + 布局抖动
- 鼠标拖拽期间虽然暂停刷新，但用户交互（hover tooltip、选中状态）丢失
- W22 pnl-curve（Canvas 组件）在数据不变时也会被 `_renderBody()` 触发 → Canvas 不必要重绘

**建议**：
- 引入**脏检查**：比较新旧数据 hash，只有相关数据变化时才重绘
- 或者实现**增量订阅**：每个组件只监听自己的 dataPaths，不用 notifyAll

#### 2.2.2 渲染触发机制过于粗糙

**问题**：
- `DataStore.subscribe()` 注册的 callback 对所有订阅路径都是同一个
- `notifyAll()` 遍历所有 subscribers，不管数据变没变
- 拖拽期间 `isDragging = true` 暂停刷新，但拖拽结束瞬间所有组件同时触发 → 可能卡顿

**建议**：
- 将 subscription 改为**路径级细粒度**：每个 dataPath 有独立的变更标记
- 引入 `requestAnimationFrame` 批量处理渲染请求，减少布局抖动

#### 2.2.3 组件间通信缺失

**问题**：组件间唯一通信方式是都读取 `DataStore.merged`。但有些场景需要直接联动：
- W06 竞价5维面板 → 接 W08 W1 开盘快照的数据
- W14 账户风控 → 从 W15 持仓数据同源
- W03 仓位计 → 读取 W16 报数的总资产

目前这些都是通过 manualData 和 shared merged 对象隐式共享，没有形式化的跨组件通信协议。

**建议**：建立**组件事件总线**（轻量），让组件可以：
- 发布事件：`DataStore.emit('position-changed', {...})`
- 订阅事件：`DataStore.on('position-changed', callback)`

或者保持简单：如果数据已通过 DataStore.merged 共享，则无需额外通信。

> **我的判断**：当前隐式共享已够用。如果引入事件总线，会增加复杂度且收益不明确。**不推荐**。

#### 2.2.4 组件注册表中 tier 映射混乱

**问题**：部分组件的 tier 与实际情况不符：

| 组件 | 声明 tier | 实际行为 | 问题 |
|------|----------|---------|------|
| W03 | `realtime` | `tier` 不在 DataStore.tiers 定义中 → 定时器不启动 | 数据无法自动刷新 |
| W15 | `realtime` | 同上 | 同上 |
| W17 | `manual` | 读 `decision.今日操作` 但数据源是 manualData | 刷新时机不明确 |
| W18 | `tick` | 只是美股涨幅展示，tick 级别过度刷新 | 浪费网络资源 |

**建议**：
- 统一 `tier` 定义：只使用 `tick/fast/manual/daily`
- 移除未定义的 `realtime`；如果 W15/W03 需要自动刷新，改为 `tick`

#### 2.2.5 `innerHTML` 安全性风险

**问题**：多个组件将用户输入（manualData 字段）直接拼入 HTML：
- W15 positions.js 第 28 行：`JSON.parse(manual['_positions'])` → 数据直接进 innerHTML
- W17 today-ops.js：用户录入的操作描述直接渲染
- W16 input-panel.js：直接渲染表单值

虽然是本地仪表盘，但如果未来接入远程数据，XSS 风险需要考虑。

**建议**：使用 `textContent` + `createElement` 替代拼接，或至少做 `escapeHTML()` 处理。

#### 2.2.6 数据文件组织

**问题**：`data/` 目录下积累了大量 `.bak*` 文件和冗余文件：

```
data/dashboard_data.json.bak_test
data/dashboard_data.json.bak_20260513_0846
data/dashboard_data.json.bak_0938
data/dashboard_data.json.bak_auction
data/dashboard_data.json.bak_1030
data/dashboard_live.json
```

**建议**：
- 归档 `.bak*` 到 `data/backup/`
- 建立 `data/` 目录的 `.gitignore` 规则

## 3. 信息架构与时间维度

### 3.1 组件时间维度分析

这是交易仪表盘的核心考量 — 不同的组件服务于盘中不同时间粒度的决策：

| 决策时段 | 对应组件 | 分辨率 | 关注点 |
|---------|---------|--------|--------|
| **竞价 (9:15-9:30)** | W06 竞价5维, W07 高潮保护, W20 AI 竞价研判 | 一次性 | 情绪预处理 |
| **W1窗口 (9:30-10:00)** | W08 W1早盘确认, W18 锚定股, W04 市场全景 | 最高频 5s | 执行买入 |
| **上午观察 (10:00-11:30)** | W10 板块热力, W05 情绪, W09 W2观察 | 低频 | 持仓观察 |
| **午盘 (11:30-13:00)** | W19 午盘复核, W16 报数 | 一次性 | 盘中修正 |
| **W2窗口 (14:00-14:45)** | W09 W2实时观察, W14 风控 | 高频 5s | 执行卖出 |
| **尾盘 (14:45-15:00)** | W20 AI 尾盘研判, W17 今日操作 | 一次性 | 收盘决策 |
| **收盘后** | W02 风格检测, W21 涨停梯队, W22 收益曲线 | 一次性 | 复盘 |

### 3.2 ✅ 做得好的

- 时段划分清晰：W01 时段时间线提供了准确的盘中时段导航
- 决策类组件集中在关键窗口期（W1/W2）
- 数据类组件提供辅助参考

### 3.3 ❌ 信息架构问题

#### 3.3.1 组件默认布局缺少决策工作流引导

**问题**：当前 22 个组件通过 GridStack 自由摆放。虽然灵活，但**缺乏默认布局的决策引导**。新用户打开仪表盘时，不知道应该把哪些组件放在视野中心。

**建议**：
- 设计 3 套 **角色预设布局**：`全屏看盘` / `专注交易` / `复盘分析`
- 预设布局默认包含推荐组件 + 排列方式
- 在顶部栏添加预设切换（目前 1/2/3/4 快捷键已定义但预设面板被移除，需重建）

#### 3.3.2 组件类别混排影响视觉认知

**问题**：决策类（decision）和数据类（data）的区分在注册表中清晰，但在实际视图中没有足够区分度。

**建议**：加强**类别视觉区分度**：
- 标题栏左侧 3px 色条已有（蓝/绿/红/灰），但色差在快速扫描时辨识度不够
- 增加类别标签：`🎯 决策` / `📊 数据` / `🔒 风控` / `🛠 工具`
- 或者在组件右上角增加类别小标识

#### 3.3.3 信息层级扁平化 — 缺少"关键指标"区

**问题**：所有 22 个组件在 GridStack 中平铺。但交易决策中，有些信息是**秒级需要**的（实时盈亏、仓位、情绪值），有些是**分钟级**（板块、自选池），有些是**小时级**（涨停梯队、收益曲线）。

**建议**：
- 增加**顶部固定栏关键指标 Pills**：实时盈亏、仓位、情绪值、总资产
- 这些 Pills 始终可见，不依赖 GridStack 滚动
- 类似券商软件的固定顶栏

## 4. 用户人因工程评估

### 4.1 视觉层次

#### 4.1.1 ✅ 颜色体系

```
红涨绿跌 ✓         (A股标准)
紫色 accent ✓      (一致性强)
4 级语义色 ✓       (info/warn/danger/special)
4 级阴影 ✓         (card/elevated/drag/modal)
```

色彩设计是整套系统最成熟的部分。theme.css 的自定义属性体系清晰，4 级阴影层级感分明。

#### 4.1.2 ❌ 字号层级不足

当前字号方案：
```
--fs-micro: 9px   → 极小
--fs-label: 10px  → 标签
--fs-body: 12px   → 正文
--fs-header: 13px → 标题
--fs-subtitle: 15px → 副标题
--fs-kpi: 22px    → KPI 数值
--fs-hero: 28px   → 大数值（未实际使用）
```

**问题**：
- `fs-body (12px)` 对盘中快速扫描太小。在高分屏（Retina）上尤其吃力
- KPI 数字 22px 作为关键决策数字（比如实时盈亏、情绪值）视觉冲击力不够
- 同一组件内正文和数字对比度不足

**建议**：
- 关键 KPI 提升至 28px（`--fs-hero`）
- 正文基础字号从 12px → 13px
- 增加数据/决策的文字大小差异化：数据类用 12px，决策关键数字 28px

### 4.2 交互反馈

#### 4.2.1 ✅ 已经实现的

- 拖拽高亮（`--shadow-drag`）
- 悬停状态（`--bg-hover`, `:hover` 过渡）
- Toast 通知（撤销删除、保存、添加组件）
- 组件折叠（collapse 按钮）
- 连接状态指示器（顶部 dot）

#### 4.2.2 ❌ 缺失的交互反馈

**无加载态**：当数据未就绪时，组件区域显示旧数据或无提示。
- 5s tick 数据拉取中 → 组件仍然显示空白或崩坏
- file:// 模式无网络 → 组件静默失败

**建议**：
- 在 widget-base 中增加**加载骨架屏**：`render()` 之前显示 Skeleton
- 组件数据过期显示"数据延迟"警告
- 统一错误显示模式：`widget-error` 区域显示具体错误信息（而非"组件加载失败"）

**无展开/全屏态**：组件只有折叠和默认两种状态  
*"想看 W22 收益曲线的大图" → 只有一种尺寸*

**建议**：
- 增加组件**全屏模式**：双击标题栏或增加全屏按钮
- 全屏后占据整个视口，数据仪表盘层自动隐藏

### 4.3 操作效率

#### 4.3.1 ✅ 快捷键系统

`R` 刷新 / `P` 跳转报数 / `Ctrl+S` 保存 / `A` 菜单 / `Ctrl+Z` 撤销删除

快捷键覆盖了核心操作，但缺少：  
- `Ctrl+F` 搜索组件功能  
- 翻页/跳转快捷键  

#### 4.3.2 报数面板（W16）UX 瓶颈

**问题**：
- 23 个字段在 5 列网格中，字段间无分组/分类
- 字段排序混乱（先总资产/资金，中间跳转情绪，再到观察股）
- 输入触发 localStorage 存储但无保存提示
- "刷新全部数据"按钮在底部，与输入区距离远

**字段分组建议**：

```
账户头寸（3个）：总资产 | 可用资金 | 总盈亏
情绪指标（5个）：情绪值 | 涨停收益 | 连板收益 | 炸板收益 | 赚钱效应
盘面数据（6个）：上涨 | 下跌 | 涨停家数 | 跌停家数 | 晋级率 | 封板率
连板生态（4个）：风险值 | 最高板 | 次高板 | 梯队
盘中观察（6个）：W1观察1-3 | W2观察1-3
```

#### 4.3.3 全局搜索/导航缺失

**问题**：22 个组件散布在 GridStack 画布中。当组件数量多时，找特定组件需要滚动浏览。

**建议**：
- 顶部栏增加**组件搜索框**：`Ctrl+F` 聚焦，输入组件名自动滚动定位
- 或者增加侧边导航缩略图（类似设计工具的图层面板）

## 5. 22个组件逐一诊断

> 评分标准：1-5 分，5 为最佳  
> **Useful** = 信息对决策有用性 / **Clear** = 信息呈现清晰度 / **Performant** = 渲染性能

### 5.1 工具类

#### W01 时段时间线 ⭐ 4.5/5

| 维度 | 评分 | 诊断 |
|------|------|------|
| Useful | 5 | 盘中导航核心，7 段制准确 |
| Clear | 5 | 进度条 + 倒计时 + 时段名，一目了然 |
| Performant | 4 | 每秒计算 DOM 更新时间？可优化为 1 秒更新而非每次 render |

**优化建议**：
- **低优先级**：增加午休时间段的视觉分隔（虚线）
- **低优先级**：支持点击时间段跳转到对应组件（点击 "W1窗口" 聚焦 W08）

#### W16 报数面板 ⭐ 3.5/5

| 维度 | 评分 | 诊断 |
|------|------|------|
| Useful | 5 | 数据入口，核心功能 |
| Clear | 3 | 23 字段无分组，视觉杂乱 |
| Performant | 5 | 浮窗模式，不随 tick 刷新 |

**优化建议**：
1. **字段分组**（高优先级）
2. **字段排序优化**：按"账户→情绪→盘面→连板→观察"顺序
3. **保存反馈**：输入后自动保存 + Toast 提示
4. **批量粘贴支持**：允许一次性粘贴多个字段

### 5.2 决策类

#### W02 风格检测卡 ⭐ 3.5/5

| 维度 | 评分 | 诊断 |
|------|------|------|
| Useful | 4 | 风格判定是仓位基准 |
| Clear | 3 | 维度+分值+晋级率+分配表 信息密度高但缺乏视觉层级 |
| Performant | 4 | daily 级，不频繁刷新 |

**优化建议**：
1. **增加可视化仪表**：用圆形进度条代替纯文字数字
2. **信号强度指示器**：将"连板信号强度"/"趋势信号强度"转化为直观的仪表盘

#### W03 三层仓位计 ⭐ 4/5

| 维度 | 评分 | 诊断 |
|------|------|------|
| Useful | 5 | 仓位控制是交易生命线 |
| Clear | 4 | 三层视觉清晰（总仓位→分配→实际），但阻塞原因不够醒目 |
| Performant | 3 | tier='realtime' 未定义，定时器不启动 |

**优化建议**：
1. **修复 tier**：改为 `tick` 以启用自动刷新
2. **阻塞原因高亮**：熔断/连亏等阻塞条件用红色横幅显示
3. **仓位仪表化**：用进度条+百分比双通道展示

#### W06 竞价5维面板 ⭐ 4/5

| 维度 | 评分 | 诊断 |
|------|------|------|

## 总结

### 核心发现

1. **架构底子好**：零构建 + 组件化 + 错误隔离 + 三层数据合并的设计在同类看板中属于优秀水平
2. **最大瓶颈**：全量 `innerHTML` 赋值在 tick 级 5s 刷新下是最大的性能瓶颈
3. **最大体验提升点**：W16 报数字段分组 + 顶部关键指标固定栏 + 信号灯视觉增强
4. **维护性风险**：W22 903 行、W21 502 行、W08 400 行 — 大型组件需要拆分或重构

### 建议的执行顺序

```
Phase 1（基础设施） → Phase 2（信息架构） → Phase 3（决策增强） → Phase 4（完善）
   3天                   3天                   4天                   3天
```

**总估算**：约 13 个工作日  
**最小可行发布**（如果时间紧迫，Phase 1 + Phase 2 的 W16 字段分组 + 顶部 Pills 即可带来 70% 体验提升）
