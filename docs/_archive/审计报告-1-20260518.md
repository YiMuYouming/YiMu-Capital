## 二、P0 问题 — 架构性硬伤（必须修复）

### P0-1：poll_live.py 是"上帝脚本"（1663 行 / 58KB）

一个脚本同时在做以下所有事：

| 责任 | 行数约 | 输入 | 输出 |
|------|--------|------|------|
| PyTDX 连接管理（IP轮询+重试） | 50 | TDX 服务器 | 连接池 |
| 个股实时行情（5s轮询） | 100 | `get_security_quotes` | live_quotes |
| 三大指数（5s轮询） | 80 | `get_index_bars` | live_index |
| 15min 量价（5min更新） | 120 | `get_index_bars` | 上证/深证/创业15min |
| 昨日基线 | 60 | `get_index_bars`(日K) | yesterday_baseline |
| 全市场量比 | 40 | 当日/昨日15min 计算 | live_index.量比 |
| 涨跌家数 | 50 | `get_security_list` + 遍历 | live_index.上涨/下跌家数 |
| 板块数据（东方财富） | 100 | push2.eastmoney.com | live_sectors |
| 板块数据失败回退 | 20 | 无数据 | — |
| 均线计算（MA5/MA10/MA20/60min） | 80 | `get_security_bars` | 缓存 |
| 量比计算 | 30 | 成交量缓存 | 缓存 |
| SQLite 写入 | 30 | 计算结果 | pnl.db |
| JSON 写入 | 20 | 计算结果 | dashboard_live.json |
| 缓存管理 | 30 | 各缓存 | 全局变量 |
| 板块名称→TDX代码映射表 | ~100 | 硬编码字典 | sector_index 查询 |
| 沪深京 5000+ 只全市场扫描 | 50 | `get_security_list` | 广度数据 |
| 辅助函数 | 200+ | — | — |

**后果**：
- 1663 行的单文件，修改任何一处都可能触发复杂的副作用
- 无法独立测试/替换某个子模块（比如把东方财富换成其他来源）
- 排查故障时需要通读全部代码

### P0-2：同一数据字段存在最多 3 个竞争来源

以 `情绪值` 为例：

```
├─ 来源A: 复盘笔记 → dashboard_data.json → baseData.sentiment.情绪值
│  更新频率: 每日盘后
│  优先级: 高（SSOT 基线）
│
├─ 来源B: W16报数面板手工录入 → localStorage → manualData['情绪值']
│  更新频率: 盘中随时
│  优先级: 中（手工覆盖）
│
└─ 来源C: 涨跌家数反推 → store.js merge() 中自动计算
   更新频率: 每次 merge()
   触发条件: manualData['上涨'] + manualData['下跌'] 存在且 manualData['情绪值'] 为空
```

store.js 中为了处理这种竞争，已经有了一个"补丁"：
```js
// 情绪值：只覆盖如果 baseData 没有情绪值（日报SSOT优先，防旧缓存覆盖）
if (manualData['情绪值'] && (!src.sentiment || !src.sentiment['情绪值'])) {
```

注释里的"防旧缓存覆盖"直接承认了数据时序问题——**如果 manualData 里有旧缓存，而 baseData 里有新的复盘数据，旧的手工数据会错误地覆盖最新的复盘数据。**

同样的**多源竞态**问题也存在于：

| 字段 | 候选来源 | 竞争数量 |
|------|---------|---------|
| 情绪值 | 复盘笔记 / 手工录入 / 涨跌家数反推 | **3** |
| 赚钱效应 | 复盘笔记 / 手工录入 / 涨停收益自动判定 | **3** |
| 涨跌家数 | 复盘笔记 / 手工录入 / PyTDX 实时 | **3** |
| 封板率 | 复盘笔记 / 手工录入 | **2** |
| PnL (总资产/总盈亏) | Excel JSON SQLite | **3** |

## 三、P1 问题 — 结构性问题（建议修复）

### P1-1：数据管线时序错位

看板在盘前 9:00 启动时的数据状态：

```
dashboard_data.json (今日复盘 → 昨日收盘基线) ✅ 最新
dashboard_live.json (5s轮询 → 今天实时) ✅ 最新
embedded-data.js (兜底 → 数日前) ⚠️ 可能过时
```

看板在盘中 10:00 时的数据状态：

```
dashboard_data.json (昨日复盘基线)     ⚠️ 今天还没跑复盘
dashboard_live.json (5s轮询)           ✅ 实时
```

看板在收盘后 15:10 时的数据状态：

```
dashboard_data.json (昨日复盘基线)     ⚠️ 今天还没跑复盘
dashboard_live.json (最后轮询数据)     ⚠️ 已经收盘
```

**关键问题**：没有任何机制保证 `dashboard_data.json` 的"今日数据"在收盘后被重新生成。如果 gen_dashboard_data.py 没跑，看板一直看的是昨天的数据。

实际验证：`data/dashboard_data.json` 的更新时间是 **08:45 今天**（已更新），但 `data/dashboard_live.json` 的更新时间是 **May 15 18:39**（3 天前）。

### P1-2：bridge.py 是 HTTP 服务器 + 文件写入器 + AI 客户端 + 数据代理

bridge.py（19KB）的职责清单：

| 功能 | 路由/功能 | 代码行数 |
|------|----------|---------|
| 静态文件服务器（SimpleHTTPRequestHandler） | 全部 URL | 10 |
| PnL 数据 API | GET /api/pnl?range=&index= | 30 |
| PnL 摘要 API | GET /api/pnl/summary | 15 |
| 交易记录 API | GET /api/trades | 15 |
| 记流水同步（写入JSON + SQLite） | POST /api/sync | 55 |
| 复盘重新生成 | POST /api/refresh | 25 |
| AI 研判（调用DeepSeek + 写JSON + 写SQLite） | POST /api/llm | 70 |
| API 配置加载 | ~/.claude/settings.json | 20 |
| ReAct 信号验证引擎 | 内联 | 80 |
| System Prompt | LLM指令文本 | 35 |

**数据写入点**：
- `POST /api/sync` → 写入 `dashboard_data.json` + `pnl.db`
- `POST /api/llm` → 写入 `llm_insights.json` + `pnl.db`
- `GET 静态文件` → 透传所有文件

**这是 server + writer + AI client 的三合一混合体**，违背了单一职责原则。

### P1-3：数据时效性完全无标记

22 个 Widget 消费 merged 数据时，**没有任何字段告诉它们数据是什么时候更新的**：

```js
// 示例：W05情绪仪表盘读取情绪值
DataStore.get('sentiment.情绪值')  // → 32
// 这是今天的还是昨天的？不知道！
```

`meta` 字段中有 `updated` 时间戳（如 `2026-05-18T08:45:21+08:00`），但没有任何 Widget 检查它。如果 gen_dashboard_data.py 三天没跑，Widget 不会知道它在读过期数据。

### P1-4：18 个 .bak 残留文件（占 22%）

按位置统计：

| 位置 | .bak 文件 | 说明 |
|------|-----------|------|
| `data/` | 6 | dashboard_data.json 的 5 个旧版本 + auction 备份 |
| `scripts/` | 5 | poll_live.py 2个版本 + poll_iwencai + snapshot + db |
| `widgets/` | 4 | auction-5d + pnl-curve + w1-check + widget-registry |
| 根目录 | 3 | index.html 2个版本 + store.js |

此外还有一个 `widgets/sector-heat.js.new`（草稿文件）。

**全部 18 个备份文件加起来的 Git 历史里都有记录**——它们完全是多余的。

### P1-5：store.js 的 SSOT 溯源覆盖率极低

`DataStore.getSSOT(path)` 只映射了约 10 个路径，但系统有 50+ 个 dataPaths：

```js
getSSOT: function(path) {
  var map = {
    'style.总分':         { source: 'style_detect.py → dashboard_data.json', ... },
    'sentiment.情绪值':    { source: '同花顺APP→手工录入 / 涨跌家数反推', ... },
    'live_index.*':       { source: 'PyTDX → poll_live.py', ... },
    // ... 总共只有约 10 个映射
  };
  return map[path] || { source: '—', freq: '—', owner: '—' };
}
```

剩下的 40+ 个数据路径返回 `{ source: '—', freq: '—', owner: '—' }`，等于没有溯源。

### P1-6：数据格式不统一

merge() 中有专门的 `clean_value()` 函数处理各种格式差异：

| 格式问题 | 例子 | 处理方式 |
|---------|------|---------|
| 数字 vs 字符串 | `情绪值: 32` vs `涨停收益: "-0.9%"` | 手工判断 |
| 括号注释 | `"一般（涨停收益2.92%一般）"` | 正则剥离 |
| 百分号 | `"10.91"` vs `"10.91%"` | 有条件地转数字 |
| 斜杠分隔 | `"126 / 98"` | 取第一个数字 |
| 字段名依赖 | `"最高板"` 保留括号，`"情绪值"` 去掉括号 | 按 whitelist 区分 |

**同样一个字段（如 `涨停收益`），在 dashboard_data.json 里可能是纯数字 `-0.9`，在 manualData 里可能是字符串 `"-0.9%"`，在 liveData 里可能是 `"—"`。** store.js merge() 的逻辑越来越复杂来解决这些差异。

## 七、总结

### 一句话

> **当前架构的核心问题不是"少做了什么"，而是"谁都能写数据"——5 条管线往 4 种存储里写，22 个 Widget 随机读取，没有统一的数据网关。**

### 最严重的三个问题

1. **poll_live.py 1663 行** — 既是数据采集器，又是指标计算器，还是持久化写入器。拆成 4-5 个独立模块是当务之急。
2. **情绪值有 3 个数据源打架** — 复盘笔记、手工录入、涨跌家数反推同时往同一个字段写。store.js 的"防旧缓存覆盖"补丁证明了设计时就知道有问题。
3. **板块数据是"假实时"** — 东方财富 API 境外 IP 受限，回退到昨天的基线。但 Widget 仍然以 30s 频率刷新，用户以为在看实时行情。

### 文档与实际代码的偏差

| 项目 | 文档说 | 实际是 |
|------|-------|-------|
| 数据层数 | 3 层 | 5条管线+2个辅助 |
| 存储方式 | JSON | JSON+SQLite+localStorage+Excel |
| 数据来源 | 复盘笔记+PyTDX+手工 | PyTDX+东方财富+问财+DeepSeek+手工+Excel |
| 组件数 | 19 | 22（+3） |
| SSOT 字段 | 全覆盖 | 10/50+ |
| 板块数据源 | 东方财富 | 东方财富（境外受限→基线） |
| YM-data-pipeline 状态 | 统一数据管道 | poll_iwencai使用，poll_live静默fallback |
