# 弈沐资本看板 V3.1 稳定性升级计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.  
> 日期：2026-05-28  
> 定位：V3.1 不是大改版，是“云端生产 + 本地预览 + 数据回流”的稳定性收口。  
> 主原则：稳定第一，简单第二，样式第三；不新增复杂服务器和主人本机长期中转依赖。

**Goal:** 让云端 8088 能稳定承担生产看板，本地 18088 能安全预览代码，日内成交、快照和收益曲线不断，其他 agent 可按任务清单接手运维。

**Architecture:** 保留当前 Python bridge + APScheduler + SQLite + 原生 JS/GridStack 的架构。云端作为生产账本，本地作为开发和复盘生成入口；数据文件通过受控脚本同步，不通过 git。V3.1 只补运维闭环、健康语义、账户基准审计和小范围 UI 状态，不重写核心组件。

**Tech Stack:** Python `unittest` / SQLite backup API / Bash or Python ops scripts / 原生 JS / CSS variables / Agent Board。

## 1. 当前事实基线

### 本地

- `localhost:8088` 当前是 SSH tunnel，转发到 hermes 云端。
- `localhost:18088` 当前是本地只读预览代理，加载本地代码，GET 数据读云端，写请求被拦截。
- 本地工作区存在真实运行数据变动：`data/dashboard_data.json`、`data/pnl.db`、`data/pools.json`、`data/sentiment_auto.json`、多份 `data/*.bak*`。
- 本地代码 HEAD：`bd34a27 docs: document cloud trading runbook`。
- 本地运行数据不应被清理、reset 或提交。

### 云端 hermes

- 服务：`yimu-live-dashboard.service` 为 `active`。
- 云端仓库 HEAD：`3fc2697 fix: restore market overview baseline compare`。
- `origin/main`：`bd34a27 docs: document cloud trading runbook`。
- 云端分叉：`HEAD...origin/main = 1 ahead / 4 behind`。
- 云端工作区存在真实运行数据变动和一个代码文件变动：`widgets/market-overview.js`。
- `/api/health` 返回：
  - `critical_ok=true`
  - `trade_entry_allowed=true`
  - `status=unhealthy`
  - `llm_config.status=missing`
- 这说明健康总状态和关键可交易状态语义还不一致，容易误判。

### 账户与收益

- `/api/account/state` 和 `/api/pnl/summary` 可返回，`valuation_complete=true`。
- 今日成交已进入云端账本。
- 当前持仓 `002049 紫光国微` 的 `_day_start_price=null`，今日 PnL 拆分不可用。
- 今日清仓 `002436 兴森科技` 的 `realized_today_pnl=null`，清仓收益拆分不可用。
- 总资产和曲线能跑，但分项日内收益解释还不完整。

### 数据源

- 云端香港节点不适合作为 PyTDX 裸 TCP 生产源。
- 目前 Eastmoney/Tencent/iwencai/hot_list fallback 足够保证核心曲线和节点不断。
- 不建议为 PyTDX 立刻引入主人本机中转或新服务器；V3.1 先把 fallback 生产链做稳定。

### UI 与样式

- 顶栏已有健康状态，但 `status=unhealthy` 与 `critical_ok=true` 的关系不清晰。
- 18088 和 8088 在视觉上还不够明确，主人容易混淆生产和预览。
- `store.js` 数据源说明仍有部分 PyTDX 历史口径，和云端 fallback 现实不完全一致。
- 部分组件仍有内联样式和密集文本，但这不是 V3.1 P0。

## 2. V3.1 成功标准

V3.1 完成时必须满足：

1. 云端 git 分叉被清楚盘点并收口，后续部署可以用一个标准流程完成。
2. 云端运行数据仍保留，未因 git 操作丢失。
3. `/api/health` 不再因为非关键项如 LLM token 缺失而误报生产不可用。
4. 健康 API 能明确区分：
   - 系统能否服务
   - 能否录入交易
   - 哪些数据处于降级
   - 哪些收益字段只是分项不可用
5. `day_start_price` 覆盖率有只读审计，缺失代码能被一眼发现。
6. 开盘前生成基线、同步上云、验收可以一条命令或一个脚本完成。
7. 收盘后云端 SQLite 一致性备份、拉回本地、验收可以一条命令或一个脚本完成。
8. 8088 和 18088 在页面上有明确模式标识，避免误操作。
9. W04、W15、W22、顶栏的降级展示不再把未知值显示成 0。
10. 所有改动有对应测试或只读验收命令，真实 8088 不做测试性写请求。

## 3. 禁止事项

- 禁止 `git reset --hard`、`git clean` 清理云端或本地现场。
- 禁止把本地旧 `data/pnl.db` 覆盖云端生产账本。
- 禁止对真实 8088 发测试性 `POST`、批量纠错、压力测试或实验性日结。
- 禁止用成本价猜测 `day_start_price`。
- 禁止把主人本机 PyTDX 转发作为长期生产依赖。
- 禁止为了样式重构大面积改组件结构。
- 禁止把 `data/*.db`、盘中快照、收益曲线当作代码通过 git 发布。
