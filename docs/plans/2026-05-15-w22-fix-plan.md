## P0 — 数据逻辑错误（必须修）

### P0-1 `query_pnl()` week/month 路由错误 `scripts/db.py:125-213`

**根因**（稳米发现）：`query_pnl('week')` 和 `query_pnl('month')` 走 `intraday_snapshots`，返回的是 5 分钟快照的 `pnl_pct`（当日累计浮动盈亏%）。前端取最后一个点作为"本周收益"，得到的是最后一天的日内值而非周累计。

**举例**：周一收盘 -1%，周二 +0.5%，周三 +1.2%
- 当前显示："本周收益 +1.2%"（周三单日值）
- 正确应为：`(1-0.01)×(1+0.005)×(1+0.012)-1 = +0.69%`

**修复**（稳米方案 C）：week/month/quarter/year 统一走 `daily_summary`，只有 today 走 `intraday_snapshots`。前端拿到日频数据后自己做 TWR 连乘。

```python
# db.py query_pnl(): 统一路由逻辑
if range == 'today':
    # 走 intraday_snapshots（不变）
elif range == 'all':
    # 走 daily_summary（不变）
else:
    # week/month/quarter/year — 全部走 daily_summary
    rows = _exec("""SELECT date, pnl_pct, {idx_field} AS bm_pct, pos_pct, nav
        FROM daily_summary WHERE date >= ? ORDER BY date""", (from_date,))
    return {'type':'daily', 'labels':[...], 'portfolio':[...], 'benchmark':[...], 'position':[...], 'nav':[...], 'dates':[...]}
```

**注意**：quarter/year 当前已经走 daily_summary，但 week/month 不是。改完后 week/month 也返回 `type:'daily'`，数据点从几百个变成几个（每天一个），图表从折线变为柱状——和 quarter/year 一致。

### P0-2 总资产为 0 时 NaN 防御 `pnl-curve.js:305-308`

**问题**（稳米发现）：`totalAsset` 来自 W16 报数面板同步，如果 bridge 没开或没同步过，值为 0。此时 `pnlPct = pnlAmount / 0 → Infinity`，KPI 全部显示 NaN%。

**修复**：在 `_updateKPI()` 的除法和仓位计算前加 0 值防御：

```javascript
var ta = s.totalAsset;
if (!ta || ta <= 0) {
  // 尝试从 _pnlSummary 或 _posCache 推算
  if (mv > 0 && posPct > 0) ta = mv / (posPct / 100);
}
// 还是 0 → 显示"—" 而非 NaN
if (!ta || ta <= 0) {
  asset.textContent = '—';
  pnlEl.textContent = '—';
  posEl.textContent = '—';
  return;
}
```

### P0-3 `rollup_daily()` NAV 链防御 `poll_live.py:1285-1312`

**问题**：`'nav': 1.0` 硬编码。目前 NAV 链正确是因为 backfill 先填充了数据。但新交易日 rollup 跑在 backfill 前面就会破坏 NAV 链。

**修复**：
```python
prev = _exec("SELECT nav FROM daily_summary WHERE date < ? ORDER BY date DESC LIMIT 1", (today,))
prev_nav = prev[0]['nav'] if prev else 1.0
new_nav = round(prev_nav * (1 + pnl_pct/100), 6)
```
同时补全 `sz_pct` 和 `cy_pct`——分别调 `query_pnl('today', 'sz')` 和 `query_pnl('today', 'cy')` 取末点。

**问题**（稳米发现）：`onResize()` 无参调用 `this._drawChart()`，`_drawChart` 第 559 行 `if (!chartData) return` 直接退出，resize 后图表不刷新。


### P1-2 合并重复的 `/api/pnl?range=all` 请求 `pnl-curve.js`

**问题**：`render()` 里 `_posCache`（L99）和 `_allDailyData`（L124）发了两条相同请求。`_drawPosChart()` 在缓存未就绪时还会再发一条（L451-457）。极端情况 3 次相同请求。

**修复**：合并为一个 Promise，同时喂给 `_posCache`、`_allDailyData`、`_updateDrawer`、`_updateSummary`：

```javascript
// render() 中：发起一次，多处消费
if (!self._allDataPromise && location.protocol !== 'file:') {
  self._allDataPromise = fetch('/api/pnl?range=all&index=sh')
    .then(function(r) { return r.json(); });
}
if (self._allDataPromise) {
  self._allDataPromise.then(function(d) {
    self._posCache = d;
    self._allDailyData = d;
    self._updateDrawer(d);
    self._updateSummary();
  });
}
// _drawPosChart() 中去掉独立的 fetch 逻辑，只读缓存
```

### P1-4 抽屉累计行 & 回撤修复 `pnl-curve.js:375-423`

**两项修复合并**：
1. 累计行从 `_allDailyData` 全量日频数据计算 TWR（而非取 5 个时段末点连乘）
2. 累计回撤从全时段序列算最大回撤（而非 `Math.min(五个时段的dd)`）

```javascript
// 累计行：全时段 TWR + 真实 maxDD
var cumP = 1.0, cumB = 1.0, pk = -Infinity, cumDD = 0, rp = 0;
for (var i = 0; i < allDailyData.portfolio.length; i++) {
  cumP *= (1 + allDailyData.portfolio[i] / 100);
  cumB *= (1 + allDailyData.benchmark[i] / 100);
  rp = (cumP - 1) * 100;
  if (rp > pk) pk = rp;
  if (rp - pk < cumDD) cumDD = rp - pk;
}
// render: cumPnl=(cumP-1)*100, cumBm=(cumB-1)*100, cumDD
```

### 新 P0-4: `pnl_pct` 在 `intraday_snapshots` 中是每日浮动盈亏%，不是真正的时间加权收益率

**位置**: `poll_live.py:1245-1272` (`log_pnl_snapshot`)

**问题**: 每 5 分钟快照写入 `pnl_pct = pnl_amount / total_asset * 100`，这是"当前持仓浮动盈亏 / 总资产"——本质上是当日仓位的浮动盈亏，不是时间加权收益率（TWR）。TWR 需要用净值（NAV）来计算：`(当日净值 - 前日净值) / 前日净值`。

在有资金进出的场景下，`pnl_pct` 作为快照记录的"当日收益%"是不准确的。它反映的是"以当前总资产为分母的持仓盈亏率"，而不是"当日账户净值变化率"。

**影响**:
- `rollup_daily()` 用 `data['portfolio'][-1]`（最后一个快照的 `pnl_pct`）作为日收益率写入 `daily_summary.pnl_pct`
- 如果下午 14:00 持仓亏了 1 万（-1%），但 14:30 行情反弹最终收盘+0.5%，`pnl_pct` 快照记录的会是 14:30 的值而非收盘净值变化
- 更根本的问题：快照 `pnl_pct` 不是 TWR，所以即使 `query_pnl` 的 week/month 路由修对了，日频数据的 `pnl_pct` 本身也不是正确的 TWR

**修复方向**:
1. `log_pnl_snapshot` 中维护一个 `nav` 字段（真正的时间加权净值）：当日第一个快照 `nav = 1.0`，后续快照 `nav = 前一快照nav × (1 + 当日累计pnl_pct/100)`（盘中用日内 `pnl_pct` 累乘）
2. 日终 `rollup_daily()` 取 `nav[-1]`（收盘净值）和 `nav[0]`（开盘净值），计算 `日TWR = (nav[-1] - nav[0]) / nav[0]`，写入 `daily_summary.pnl_pct`
3. `intraday_snapshots` 的 `pnl_pct` 字段改为"当日累计浮动盈亏%"（当前逻辑），`nav` 字段才是真正的盘中净值

**验收**: 日终 rollup 写入的 `pnl_pct` = `(收盘NAV - 开盘NAV) / 开盘NAV × 100`，而非"最后一个快照的浮动盈亏%"。

### 新 P0-5: `rollup_daily()` 未使用 `index` 参数——三种指数日收益全部写 0

**位置**: `poll_live.py:1283` 和 `scripts/bridge.py:197-212`

**问题**: `rollup_daily()` 内部调用 `db_query_pnl('today')`，但 `query_pnl('today')` 使用默认 `index='sh'`。这意味着：
- 深证成指 `sz_pct` 永远是 0（`rollup_daily` L1306）
- 创业板指 `cy_pct` 永远是 0（`rollup_daily` L1307）
- `daily_summary` 表的 `sz_pct` 和 `cy_pct` 列在每日 rollup 后仍为 0（除非 backfill 手动补过）

前端 W22 切换到深证/创业板对比时，`benchmark` 数据来自 `intraday_snapshots.sz_pct/cy_pct`（盘中快照时写入的实时指数涨幅）——这部分是对的。但 `rollup_daily` 没有更新 `daily_summary`，导致日频数据（quarter/year 图表和抽屉数据）中的深证/创业板对比线永远为 0。

**修复方向**: `rollup_daily()` 补调 `db_query_pnl('today', 'sz')` 和 `db_query_pnl('today', 'cy')` 取各指数日涨幅，填入 `sz_pct`/`cy_pct`。已在 fix-plan P0-3 提到但需要验证。

**验收**: `SELECT date, sh_pct, sz_pct, cy_pct FROM daily_summary ORDER BY date DESC LIMIT 5` ——三列均有非零值。

### 新 P0-6: `query_pnl` week/month 路由修复后，`benchmark` 数据也错了

**位置**: `db.py:179-182`

**问题**: 修复 P0-1 后，week/month 的 `benchmark` 字段从 `intraday_snapshots.{idx_field}`（每日实时指数涨幅）变成 `daily_summary.{idx_field}`（日终 rollup 写入的指数涨幅）。这两个理论上应该相同，但：
- 如果 backfill 补数据时 `daily_summary` 的 `sz_pct`/`cy_pct` 填了 0，而 `intraday_snapshots` 有正确值，切换到深证/创业板时 benchmark 线会突变
- 更深层：周/月图表和抽屉的 benchmark 线应该反映"以周/月第一天为起点的指数累计涨幅"，但 `daily_summary.pnl_pct` 是每日独立收益率，不是累计值

**当前正确性分析**:
- `query_pnl('week')` 从 `daily_summary` 取 `sz_pct`，每行是"当日相对前一日的涨幅"
- 前端 `_updateKPI()` 对 benchmark 也做 TWR 连乘：`cB *= (1 + cache.benchmark[i] / 100)`（L351）
- 所以 benchmark 累计收益 = `(1+r1)×(1+r2)×...-1`，这是对的

**但有一个隐藏 bug**: `query_pnl` 的 `range='week'` 对 benchmark 的处理是对的前端也是对的。真正的问题是：`daily_summary` 的 `sz_pct`/`cy_pct` 永远为 0（见 P0-5）——所以切换到深证/创业板时，benchmark 线永远是平的 0%！

**修复**: 见 P0-5。

### 新 P1-6: 指数切换后 benchmark 线"断层"——`_periodCache` 按指数隔离缺失

**位置**: `pnl-curve.js:247-248`

**问题**: `_fetchChartData` 按 `period` 缓存到 `_periodCache[period]`（L247-248），但不按 `index` 区分。这意味着：
1. 用户在"本周"视图切到深证 → 发起 `/api/pnl?range=week&index=sz`
2. 缓存到 `_periodCache['week']`
3. 之后切到"本月" → `_periodCache['month']` 正常
4. 再切回"本周" → 命中 `_periodCache['week']`（深证数据）✓
5. 但如果从深证切回上证 → `_periodCache['week']` 里是深证数据！显示错误的 benchmark 线

**修复**: 缓存 key 改为 `period + '_' + index`，或清空缓存。

```javascript
var key = period + '_' + index;
if (!self._periodCache) self._periodCache = {};
self._periodCache[key] = data;

// _updateKPI 中读取时也要用 key:
var key = s.period + '_' + s.index;
var cached = (self._periodCache || {})[key];
```

**验收**: 在"本周"视图依次切换上证→深证→创业板→上证 → 上证 benchmark 线正确（不是深的值）。

### 新 P2-4: `drawer` 首次打开时"加载中"闪烁

**位置**: `pnl-curve.js:122-137`

**问题**: `render()` 中有两个竞态：
1. 首次 render：`_drawerLoaded` 初始 false → 发 fetch → `_updateDrawer` 回调时 `_periodCache['week']` 等尚未缓存（因为图表数据还在异步加载中）→ 抽屉显示"加载中..."
2. `_updateDrawer` 在 `_periodCache` 为空时显示"加载中..."，但数据已经在 `_allDailyData`（从 L124 fetch 得来）里了——只是没进 `_periodCache`

**根本原因**: 抽屉和图表抢同一个 `/api/pnl?range=all` 请求，但 `_updateDrawer` 依赖 `_periodCache`（各时段分别 fetch 的结果），而 `_periodCache` 的数据来自 `_fetchChartData`（按 period 分别发起请求）。

**修复**: `_allDailyData`（`range=all`，日频全量）里已经有了 `dates`、`portfolio`、`benchmark`、`position`——可以提前计算出各时段 TWR 并缓存，`_updateDrawer` 直接用，不需要等各 period 的 chartData。

### 新 P2-5: `rollup_daily()` 的回撤计算用错了参考点

**位置**: `poll_live.py:1290-1300`

**问题**: `peak = data['portfolio'][0]` 取日内第一个快照的 `pnl_pct` 作为回撤计算的最高点。但这是当日第一个快照的浮动盈亏%，不是当日最高净值。正确的做法应该是：先遍历找最高点，再从最高点往后找最低点。

当前逻辑等价于：`dd = pnl_pct[i] - max(portfolio[0:i+1])`，而不是标准的最大回撤算法 `max(peak - trough)`（peak 在 trough 之前）。

**但这不影响日终 rollup 结果**：因为 `pnl_pct` 是当日累计值，最后一个快照的 `pnl_pct` 就是收盘累计。只要日内没有出现比第一个快照更低的点，`max_dd` 就接近 0。真正的问题在 P0-4（`pnl_pct` 不是 TWR）。

**修复**: 用标准算法：先找 peak，再从 peak 位置往后找最大 dd。不紧急，可单独提 P2。

### 新 P2-6: 前端 `_filterByPeriod` 与后端 `query_pnl` 的 week/month 边界逻辑不完全一致

**位置**: `pnl-curve.js:217-227` vs `db.py:149-151`

**问题**: 
- 前端（`_filterByPeriod`）：`week` 用 `new Date().setDate(now.getDate() - day + 1)` 找本周一
- 后端（`query_pnl`）：`week` 用 `d = now.day - day_of_week; from_date = now.replace(day=max(d, 1))`

两者在月初边界（如 5 月 4 日周一）有差异：前端 `setDate` 可能跨月，后端 `replace(day=...)` 不会。但实际影响很小（都是找本周一），可忽略。

**真正的边界问题**：周一（day_of_week=0）时，前端 `day = 7` → 周一 `setDate(-6)` = 上月 24 日（如果本月只有 30 天）。后端 `d = 0 - 0 = 0` → `replace(day=1)` = 本月 1 日。两者差 6 天！前端会把上月最后几天也算进"本周"。

**修复**: 前端和后端用同一个日期计算逻辑，或统一用 `db.py` 的算法在后端过滤。
