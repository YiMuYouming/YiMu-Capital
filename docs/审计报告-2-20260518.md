## 第一部分：验证 DATA_ARCHITECTURE_AUDIT.md 的 5 个核心问题

### 问题 1：多 SSOT 双写不一致 ✅ 确认成立

**代码证据**：
- `bridge.py` (L246-294) 的 `do_POST /api/sync`：**同时**写 `dashboard_data.json` 和 `pnl.db trade_records`
- `gen_dashboard_data.py` (L855-878) 的 `main()`：写 `dashboard_data.json`，不写 SQLite
- `_preserve_cleared()` (L795-826) 试图在 gen 脚本中合并已有清仓数据，但这只是"补丁"而非架构解决

**严重性补充**：更严重的是 **bridge.py 写 dashboard_data.json 时不做 schema 验证** (L250-272)。JSON payload 可以带任意字段，`merge by 标的` 的逻辑只是简单的 `existing[p.get('标的')] = p`，没有字段完整性检查。如果 W16 传了一个不完整的 `positions` 条目，会直接覆盖完整数据。

### 问题 2：数据无新鲜度标记 ✅ 确认成立

**代码证据**：
- `store.js` 中的 `connectionStatus` 只有三个值：`'live' | 'polling' | 'dead'`，是全球状态而非逐字段
- `widget-base.js` (L259-276) 的 `updateTimestamp()` 实现的"过期检测"只是检查距离上次渲染的 `elapsed > tierConfig.interval * 2`，这是渲染时间检测，不是数据新鲜度
- 没有任何数据字段附带 `_freshness` 或 `_fetched` 时间戳

**有一个部分实现没有被审计提到**：`store.js` (L101-103) 在 merge 时用 `liveData['live_quotes']` 覆盖 pool items，但"—"值被跳过 (L212: `if (q['最新价'] != null && q['最新价'] !== '—')`)，所以空值不会破坏现有数据——这是一个好的防御，但不是新鲜度检测。

### 问题 3：三个松耦合管线没有统一入口 ✅ 确认成立

**代码证据**：
- `poll_live.py --watch`：独立进程，5s/30s 双频轮询
- `bridge.py`：独立进程，HTTP 桥接
- `snapshot_auction.py`：launchd 触发，独立进程
- `poll_iwencai.py --auction`：launchd 触发，另一个独立进程

**补充发现**：`poll_live.py watch_mode` (L1571-1636) 和 `gen_dashboard_data.py watch_mode` (L829-852) 都有文件监控模式。如果两者同时运行，会产生双写竞争。

### 问题 4：复盘笔记「数据附录」vs「附录A」分裂 ✅ 确认成立

**代码证据**：
- `gen_dashboard_data.py` (L136-199) 的 `parse_appendix()` 明确搜索 `## 数据附录` 章节
- (L144): `m = re.search(r'##\s*数据附录.*?\n(.*)', content, re.DOTALL)`

### 问题 5：数据源降级是隐式的 ✅ 确认成立

**代码证据**：
- `poll_live.py` (L1440-1483) 的 `build_live_data()`：`_tdx_fail_count >= 3` → 切到 easyquotation 兜底
- 这个降级逻辑嵌套在 `try/except` 中，通过全局变量 `_tdx_using_fallback` 隐式管理
- 没有配置文件、没有日志输出降级层级、前端不知道当前是哪个数据源（虽然 `meta.source` 有标注但不被前端读取）

## 第二部分：DATA_ARCHITECTURE_AUDIT.md 遗漏的问题

### 遗漏 1 ⚠️：三份 P&L 计算实现之间存在重复和分歧

有三条独立的 P&L 计算路径，从同一数据源（YiMu.xlsx）出发但可能产生不同结果：

| 路径 | 脚本 | 方法 | 输出 |
|------|------|------|------|
| A | `import_xlsx_pnl.py` | 正向追踪 cash_rel + 持仓 cost → NAV | `pnl_history.json` + `dashboard_data.json.pnl.总资产` |
| B | `backfill_history.py` | 同上方法论 + 拉取指数 | `daily_summary` SQLite 表 |
| C | `backfill_intraday.py` | 正向追踪 + 5分钟K线 | `intraday_snapshots` SQLite 表 |

**风险**：
1. **路径 A 和 B 的计算逻辑几乎相同但代码独立** — 如果修了一个的 bug 忘了修另一个，会产生 NAV 差异
2. **路径 B 的日收益率仅基于 realized PnL** (L181: `pnl_pct = round(d['realized_pnl'] / prev_total * 100, 4)`) — 不包含未实现盈亏，这在持仓跨越多个交易日时是不准确的
3. **路径 C 的 nav 字段写死为 1.0** (L264: `nav, 1.0`) — 历史日内的 NAV 为 1.0，直到 `rollup_daily()` 或 `log_pnl_snapshot()` 才修正。这意味着历史日内数据的 NAV 不可用
4. **三个脚本都有硬编码常量 `CURRENT_TOTAL = 206075`** — 如果实际总资产变化需要手动更新

### 遗漏 2 ⚠️：`poll_iwencai.py` 大部分是死代码

审计描述 poll_iwencai.py 为实时数据管线之一，但实际上：
- `watch_mode()` (L145) — 轮询模式，但从未被 launchd / crontab 使用
- `fetch_live_index()` (L45-52) — **返回占位数据** `{"note": "live_index from iwencai Q1", "last_fetch": "..."}`
- `fetch_live_quotes()` (L54-62) — **同样返回占位数据**
- `fetch_live_sectors()` (L64-69) — **同样返回占位数据**
- `build_live_data()` (L127-143) — 调用了上述三个占位函数

**真实在用**的功能只有：
- `auction_mode()` (L298-485) — 9:26 launchd 触发，更新 `decision.竞价`
- `review_mode()` (L163-183) — 盘后按需查询

> 这 100+ 行死代码可以安全删除，不影响功能。

### 遗漏 3 ⚠️：`snapshot_auction.py` 和 `poll_iwencai.py --auction` 功能重叠

两者都查询 iwencai 竞价数据但写入不同位置：

| 脚本 | 写入位置 | 数据内容 |
|------|---------|---------|
| `snapshot_auction.py` | `auction_snapshot.json` | 独立完整竞价快照 |
| `poll_iwencai.py --auction` | `dashboard_data.json decision.竞价` | 竞价 + 规则引擎判定 |

**问题**：
1. 两条竞价管线使用不同的 iwencai 查询参数，可能产生不一致的竞价结果
2. `auction_snapshot.json` 没有组件读取（没有组件声明依赖此文件）
3. 两个脚本都手动实现了 YAML frontmatter 解析（`poll_iwencai.py L479-286` 和 `gen_dashboard_data.py L94-134`），代码重复

### 遗漏 4 ⚠️：`bridge.py` 没有认证、限流、或输入验证

- CORS 设置为 `*` (L413-416)
- `/api/refresh` 端点可以触发 `subprocess.run(["python3", "gen_dashboard_data.py"], ...)` (L307-329) — **无认证即可触发耗时的脚本执行**
- `/api/llm` 端点接受任意 payload 并调用 LLM API (L331-406) — 可能被用于消耗 API 额度
- 请求体大小没有限制

虽然是本地服务风险较低，但 `/api/refresh` 和 `/api/llm` 应该有基本的 token 验证或来源检查。

### 遗漏 5 ⚠️：多个进程并发写 `dashboard_data.json` 没有文件锁

并发写入场景：
1. `bridge.py sync` 写入 `dashboard_data.json` (W16 报数触发)
2. `poll_iwencai.py --auction` 读取并重写 `dashboard_data.json` (9:26 launchd)
3. `gen_dashboard_data.py` 重写 `dashboard_data.json`

Python 的 `json.dump` + `open(... 'w')` 不是原子操作。如果在写入过程中另一进程读取，会读到不完整的 JSON。

**现有保护**：`gen_dashboard_data.py` 的 `_preserve_cleared()` 试图从旧 JSON 中恢复清仓数据。但这增加了复杂性而非解决问题。

### 遗漏 6 ⚠️：`store.js` 的轮询机制会产生"thundering herd"

`widget-base.js` (L224-237) 每个 tick/fast 组件都有一个独立的 `setInterval` 调用 `DataStore.refresh(self.tier)`。`refresh()` 内部会触发 `adapter.fetchLive()`。

如果有 10 个 tick 组件同时触发 refresh，**10 次 fetch 几乎同时发生**。虽然 `refresh()` 没有防抖，但 `fetch` 是异步的，实际不会阻塞。不过：

1. 每个 tick 周期（5s），dashboard_live.json 被读取多次（组件数倍）
2. `_refreshCount` 计数器每 12 次触发一次 base 数据重拉，多个组件可能导致过早触发
3. **没有缓存层** — 5s 内对同一个文件做 10 次 fetch

### 遗漏 7 ⚠️：`backfill_intraday.py` 的 NAV 计算有缺陷

L264：历史日内快照的 `nav` 全部写为 `1.0`：
```python
cur.execute("""INSERT OR REPLACE INTO intraday_snapshots
    (ts, date, pnl_pct, nav, sh_pct, sz_pct, cy_pct, pos_pct, mv, total_asset)
    VALUES (?, ?, ?, 1.0, ?, ?, ?, ?, ?, ?)
""", ...)
```

而 `log_pnl_snapshot()` (L1257-1264) 的 NAV 计算是连乘的：
```python
prev_nav = prev_snap[0]['nav']
prev_pnl_pct = prev_snap[0]['pnl_pct']
delta = pnl['pnl_pct'] - prev_pnl_pct
nav = round(prev_nav * (1 + delta / 100), 6)
```

后果：历史日内 NAV 全是 1.0 → `rollup_daily()` 检测到 `has_real_nav = False` → 走 fallback 路径 → 日 TWR 可能不准确。

### 遗漏 8 ⚠️：db.py 的连接管理是反模式

`_exec()` 和 `_exec_write()` 每次调用都：
1. 创建新连接 (L16)
2. 设置 row_factory (L17)  
3. 执行查询 (L19-22)
4. commit (L24)
5. close (L25)

在 `poll_live.py` 的 5s 循环中，每个周期可能调用多次 db 操作。Python sqlite3 没有连接池，频繁创建/销毁连接在小规模下可以接受但不是最佳实践。

**实际影响评估**：低。对于本地 SQLite + 单用户场景，连接开销可忽略。但如果未来 `bridge.py` 承载更多 API 请求，应该复用连接。

## 第三部分：DATA_ARCHITECTURE_AUDIT.md 中的不精确表述

### 不精确 1：SQLite 作为唯一 SSOT 的可行性评估过于乐观

审计将 SQLite 定位为"唯一 SSOT"，但 `dashboard_data.json` 包含：

- `sentiment_nodes` — 嵌套的 5 节点情绪数据（竞价/早盘/午盘/尾盘/收盘），每个节点有 ~15 个字段
- `decision.竞价` — 嵌套的子表格结构（大盘指数/市场情绪/高标竞价/方向锚定/锚定股竞价）
- `decision.早盘` / `decision.盘中` — 各种条件列表
- `sentiment` 域 — 约 20 个字段，部分来自归纳，部分来自问财实时值兜底

这些嵌套结构不适合直接映射到关系表。要么用 JSON 列（SQLite 支持但失去 schema 约束价值），要么拆成 5+ 张表（增加复杂度）。

**更实际的方案**：混合存储 — SQLite 存储结构化数据（PnL、持仓、交易记录），JSON 文件存储文档型数据（情绪节点、决策树、LLM 研判）。两者有明确的边界和同步策略。

### 不精确 2："SSE 替代行情轮询"的改动量被低估

审计说 "bridge.py 加 ~30 行 SSE endpoint":
```python
scheduler.add_job(采集行情, 'interval', seconds=5)
scheduler.add_job(采集板块, 'interval', seconds=30)
```

但 `poll_live.py` 目前的轮询逻辑有 **1600+ 行**（L1-1663），包括：
- 6 个数据源（PyTDX 个股/指数/板块/15min/涨跌分布、easyquotation 兜底）
- 4 个全局缓存（`_vol_avg_cache`, `_ma_cache`, `_60m_cache`, `_sector_ma_cache`）
- 兜底切换逻辑
- PnL 快照写入
- 全市场扫描（5000+ 只股票每 30s）

把这些搬到 bridge.py 中作为 APScheduler 任务，加上 SSE 推送，保守估计需要 500+ 行改动，不是 30 行。

### 不精确 3：现有架构 90% 合理这个结论偏高

审计结论："现有架构 90% 合理。核心问题不是选错技术栈。"

基于代码审查，我评估的合理性为 **75-80%**。原因：
- 三个 P&L 计算实现重复（-5%）
- 死代码（poll_iwencai.py 的占位函数）（-3%）
- 缺少文件锁（-3%）
- 前端"thundering herd"轮询（-2%）
- db.py 连接管理（-2%）
- 其他零散问题（-5%）

技术栈选择（纯文件 + SQLite + 手动轮询）对于单用户本地场景确实是合理的，不需要推翻。但代码质量和一致性可以改进。

## 第五部分：未被审计覆盖的改进建议

### 建议 1：合并三份 P&L 计算代码

当前 `import_xlsx_pnl.py`、`backfill_history.py` 和 `backfill_intraday.py` 共享大量相同逻辑。建议：
1. 将公共逻辑（Excel 解析、持仓时间线构建、现金追踪）提取到 `db.py` 或新文件 `pnl_calc.py`
2. 三个脚本只保留特异性逻辑（import_xlsx 写 JSON、backfill_history 写 daily_summary、backfill_intraday 写 intraday_snapshots）
3. 消除硬编码常量 `CURRENT_TOTAL = 206075`

### 建议 2：删除 poll_iwencai.py 中的死代码

删除 `watch_mode()`、`fetch_live_index()`、`fetch_live_quotes()`、`fetch_live_sectors()`、`build_live_data()`。保留 `auction_mode()` 和 `review_mode()`。

### 建议 3：增加 dashboard_data.json 文件锁或原子写入

`gen_dashboard_data.py` 的写入可以使用临时文件 + rename 实现原子写入：
```python
tmp = OUTPUT_FILE.with_suffix('.tmp')
json.dump(data, tmp.open('w'))
tmp.rename(OUTPUT_FILE)  # 原子操作（同一文件系统）
```

### 建议 4：优化 store.js 的轮询节流

在 `refresh()` 中增加去抖/节流：
```javascript
var _pendingFetch = null;
function refresh(tier) {
  if (_pendingFetch) return; // 已有进行中的 fetch
  _pendingFetch = true;
  adapter.fetchLive().then(function(live) {
    _pendingFetch = false;
    // ...
  });
}
```

### 建议 5：add audit trail for data lineage

当前没有数据血缘追踪。建议在 `dashboard_data.json` 的 `meta` 中增加每个数据域的来源记录：
```json
{
  "meta": {
    "sources": {
      "market": {"script": "gen_dashboard_data.py", "time": "..."},
      "live_index": {"script": "poll_live.py", "time": "..."},
      "sentiment": {"script": "gen_dashboard_data.py", "time": "..."},
      "decision.竞价": {"script": "poll_iwencai.py --auction", "time": "..."}
    }
  }
}
```
